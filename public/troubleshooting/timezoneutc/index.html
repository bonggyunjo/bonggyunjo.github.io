TimeZone과 UTC란#

Timezone 이란 동일한 로컬 시간을 따르는 지역을 의미한다. 쉽게 말해 일본, 한국, 대만등은 같은 타임존이다. 흔히 UTC, Asia/Seoul 등의 표기법을 많이 접해보았을텐데, 이 표기법이 바로 해당 시간이 어느 로컬 기준으로 작성했는지를 명시하는 것이다. 예를 들어 만약, 08:00 AM 이라는 시간 표기가 있을 때 로컬 타임 표기가 없으면 어떨까? 영국과 한국에서 08:00 AM 이라는 시간에 화상 회의를 한다고 발표하면 큰 혼란이 온다.

UTC란 전 세계가 공통으로 사용하는 국제 표준시이다. 한국 시간은 UTC보다 9시간 빠르므로 UTC+9 또는 KST라고 부른다.

1. LocalDateTime이란 무엇인가?#

그렇다면, LocalDateTime이란 무엇인가? LocalDateTime은 Java 8에서 도입된 날짜와 시간 API로, 이름 그대로 ‘타임존(TimeZone) 정보가 없는 로컬 날짜와 시간’을 의미한다.

쉽게 말해 연, 월, 일, 시, 분, 초 단위까지만 표현할 뿐, 이 시간이 어느 지역(국가)을 기준으로 한 시간인지에 대한 문맥(Context)이 완전히 빠져있는 데이터 타입이다. 달력에 적힌 ‘2026년 6월 11일 오후 2시 30분’이라는 글자 그 자체와 같다.

2. LocalDateTime의 치명적인 문제점#

구현을 하면서 마주친 문제점의 핵심은 다음과 같다. 단일 국가에서만, 그리고 단일 서버 한 대만 사용하는 토이 프로젝트라면 LocalDateTime을 사용해도 큰 문제가 발생하지 않을 수 있다. 하지만 글로벌 서비스나 서버가 여러 대인 분산 환경, 특히 IoT 디바이스와 통신하는 환경에서는 심각한 데이터 정합성 문제를 일으킨다.

  1. 서버의 로컬 타임존에 의존하게 된다 LocalDateTime.now()를 호출하면 코드가 실행되는 서버 OS의 타임존을 따라간다. 만약 개발자의 로컬 PC는 한국(KST)이고, 배포된 AWS EC2 서버의 기본 타임존은 UTC로 설정되어 있다면 어떻게 될까? 로컬에서는 오전 10시로 정상 저장되던 데이터가, 배포 환경에서는 오전 1시로 저장되는 대참사가 발생한다.

  2. 글로벌 서비스 및 IoT 디바이스와의 시간 불일치 해외에서 접속하는 유저가 작성한 게시물, 혹은 해외에 설치된 IoT 센서가 보낸 데이터를 처리할 때 타임존 정보가 없으면 이 데이터가 절대적인 시간 축에서 언제 발생한 이벤트인지 특정할 수 없다. 영국 센서가 보낸 08:00 AM과 한국 센서가 보낸 08:00 AM을 LocalDateTime은 동일한 시간으로 취급해 버려 시계열 데이터가 엉망이 된다.

3. 해결 방안#

해결 방안: UTC 기준의 절대 시간 사용하기 이러한 문제를 방지하기 위해 백엔드 시스템에서는 “모든 시간 데이터의 저장과 통신은 UTC를 기준으로 한다"는 원칙을 세워야 한다.

ZonedDateTime / OffsetDateTime 사용: 타임존이나 UTC와의 오프셋(Offset) 정보를 포함하는 객체를 사용하여 명확한 시점을 기록한다.

Instant 사용: Instant는 1970년 1월 1일 UTC를 기준으로 경과한 시간을 나노초 단위로 표현한다. 무조건 UTC를 기준으로 작동하므로 타임존 이슈를 원천 차단하기 가장 좋은 타입이다.

DB 타임존 일치: 애플리케이션 코드뿐만 아니라 MySQL 등 데이터베이스의 타임존 설정도 UTC로 통일하여 불필요한 변환이 일어나지 않도록 방어한다.

결론적으로, 사용자에게 화면을 보여줄 때(프론트엔드)만 기기의 로컬 타임존에 맞춰 변환해서 보여주고, 서버 내부 로직과 데이터베이스는 철저하게 UTC 기준으로 동작하도록 설계하는 것이 트러블슈팅을 줄이는 핵심이다.

4. 해결 과정#

다음과 같은 해결 방안이 있었는데, 먼저 적용한 방식은 LocalDateTime을 ZonedDateTime으로 적용했었지만 실패했었다. MySQL에선 ZonedDateTime 담을 수 있는 데이터 타입이 없기 때문이다.

그렇다면, 💡 왜 MySQL에서는 ZonedDateTime이 바로 안 먹힐까? jAVA의 ZonedDateTime은 시간 + 시간대 정보를 모두 가지고 있다. 하지만 MySQL의 날짜 타입(DATETIME,TIMESTAMP)은 시간대 정보를 저장 못한다. 그래서 JPA를 통해 ZonedDateTime을 그대로 DB에 밀어 넣으려고 하면, JPA가 알아서 시간대 정보를 잘라버리고 서버의 기본 시간대나 UTC 기준으로 시간을 변환해서 DATETIME으로 저장해버린다. 이때 나중에 DB에서 꺼내올 때 처음에 넣었던 시간대를 기억못하니(저장이 안되서) 의도치 않게 동작이 된다.

그래서 이에 모든 도메인에 대한 날짜/시간 데이터 타입을 LocalDateTime에서 Instant 타입(모든 저장과 처리는 절대적인 시간인 UTC)으로 변경하고, 사용자 화면에서 보여줄 때만 사용자의 시간대로 변환하도록 하였다.

기존#

//기존
private LocalDateTime created_at;

변경#

//변경
private Instant created_at;

이후 별도로 기존 생성되어있던 각 테이블 컬럼이나 타입들은 업데이트를 해주지 않아도 잘 동작하였다. 이는, JPA(Hibernate)가 Instant 객체를 DB에 넣을 때, 애플리케이션을 UTC 기준으로 세팅해 두어서 시간대 정보를 제외한 순수 UTC 시간의 숫자(연월일시분초)만 추출하여 기존 DATETIME 컬럼에 덮어쓰기 때문에 별도의 스키마 변경(Migration) 없이 적용이 가능하였음.

Instant는 MYSQL에서 LocalDateTime과 똑같은 타입으로 생성(DATETIME) 되기 때문에, 만일 TIMESTAMP와 같이 생성이 된다면 필드 타입을 동시에 업데이트 해주어야 하지만 이런 번거로움은 없었음.

프론트에선 format.js 내 공통 함수 formatDate 함수를 생성하여 적용되어야 할 파일에 공통 함수를 적용하였음. 단, formatDate 함수에선 .ISOString() 으로 사용하는 것이 아닌 TimeZone UTC를 제공하는 .toLocaleDateString() 을 사용해야 한다.
