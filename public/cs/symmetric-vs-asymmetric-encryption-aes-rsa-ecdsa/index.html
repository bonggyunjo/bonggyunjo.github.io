대칭키 암호화(AES-256-GCM) vs 비대칭키 암호화(RSA, ECDSA)의 키 크기와 수학적 원리

1. 한눈에 보는 핵심 원리 요약#

암호화 방식은 암복호화에 사용하는 키가 같은지 다른지에 따라 크게 두 가지로 나뉜다.

구분대칭키 (Symmetric Key: AES, DES)비대칭키 (Asymmetric/Public Key: RSA, ECC)
키 구조암호화할 때 쓰는 키와 복호화할 때 쓰는 키가 동일함공개키(Public Key)와 개인키(Private Key) 한 쌍을 사용
핵심 장점수학적 연산이 단순하여 암복호화 속도가 압도적으로 빠름공개키로 암호화하면 개인키로만 복호화 가능해 키 전달 문제 해결
치명적 한계네트워크를 통해 상대방에게 키를 안전하게 전달(Key Distribution)하기 어려움소인수분해, 타원곡선 이산대수 등 무거운 연산으로 속도가 수백~수천 배 느림

2. 동작 메커니즘 단계별 분석#

1) 대칭키: AES-256#

  • 256비트 길이의 비밀키 1개를 사용한다.
  • 데이터를 128비트 블록 단위로 쪼갠 뒤 치환(SubBytes)과 전치(ShiftRows/MixColumns) 라운드를 14회 반복한다.
  • 현대 CPU에 내장된 하드웨어 가속 명령어(AES-NI) 덕분에 기가바이트(GB) 단위의 대용량 데이터도 수 밀리초(ms) 만에 암복호화할 수 있다.

2) 비대칭키: RSA#

  • 거대한 두 소수의 곱은 계산하기 쉽지만, 그 곱을 다시 두 소수로 소인수분해하는 것은 현실적인 시간 내에 풀기 어렵다는 수학적 난제에 기반한다.
  • 안전한 보안 강도를 유지하려면 최소 2048비트 이상의 큰 키가 필요하다.

3) 비대칭키: ECC / ECDSA (타원곡선 암호)#

  • 타원곡선 위 점들의 이산대수 난제에 기반한 암호화 방식이다.
  • RSA 2048비트와 동일한 보안 강도를 단 256비트의 작은 키만으로 달성할 수 있다. 키 크기가 작고 연산 효율이 좋아 모바일 환경과 TLS 1.3의 표준으로 자리 잡았다.

4) 전자서명 (Digital Signature)#

  • 비대칭키의 역할을 거꾸로 활용하는 방식이다.
  • 송신자가 자신의 개인키로 문서의 해시값을 암호화(서명)해 보내면, 수신자는 송신자의 공개키로 이를 복호화해 검증한다.
  • 이를 통해 문서가 중간에 위변조되지 않았는지(무결성)와 실제로 해당 송신자가 보낸 것이 맞는지(신원 증명 및 부인 방지)를 확인할 수 있다.

3. 실무 Q&A: DB 개인정보 암호화에는 무엇을 쓸까?#

Q1. DB에 저장되는 주민등록번호나 계좌번호 같은 민감 개인정보 암호화에는 대칭키와 비대칭키 중 무엇을 사용하며, 그 이유는 무엇인가요?

결론부터 말하면 100% 대칭키(AES-256)를 사용한다.

보통 “비대칭키가 더 최신이고 안전해 보이니 DB 암호화에도 비대칭키를 써야 하지 않을까?“라고 생각하기 쉽지만, 실무에서는 절대 쓰지 않는다. 이유는 세 가지다.

  1. 비대칭키를 쓸 이유가 없다 (키 전달 문제가 없음)
    • 비대칭키가 탄생한 주된 목적은 “인터넷 너머의 모르는 상대방에게 비밀키를 안전하게 전달하기 위해서”다.
    • 하지만 DB 데이터를 암호화해서 넣고 다시 꺼내 복호화하는 주체는 오직 우리 백엔드 서버 자신뿐이다. 외부에 키를 전송할 일 자체가 없으므로 비대칭키의 장점이 필요 없다.
  2. 압도적인 성능 차이 (CPU 부하 방지)
    • 대칭키(AES)는 단순 치환/전치 연산이라 Intel/AMD CPU의 AES-NI 하드웨어 가속을 받아 대량 데이터도 순식간에 처리한다.
    • 반면 비대칭키(RSA)는 거대한 정수 모듈러 거듭제곱 연산 때문에 대칭키보다 수백~수천 배 느리다. 만약 회원 1만 명의 결제 계좌를 조회할 때마다 비대칭키로 복호화한다면 서버 CPU가 100%로 치솟으며 마비될 수 있다.
  3. 암호문 크기(용량) 증가 문제
    • RSA 2048비트로 암호화하면 고작 10글자짜리 계좌번호라도 최소 256바이트(2048비트) 크기의 암호문으로 불어난다. DB 스토리지 용량과 디스크 I/O 낭비가 심해진다.

참고: 백엔드 데이터별 암호화 방식 정리#

  • 비밀번호: 서버조차 원래 값을 알 필요가 없으므로 복호화가 불가능한 단방향 해시(BCrypt, SHA-256 + Salt)를 사용한다.
  • 주민번호 / 계좌번호: 화면에 보여주거나 송금 API에 넘길 때 원문으로 복호화해야 하므로 양방향 대칭키(AES-256)를 사용한다.

4. 백엔드 실무 결정 트리와 하이브리드 암호화#

실무에서 암호화 방식을 선택할 때는 아래 기준(결정 트리)으로 판단하면 명확하다.

[ 어떤 암호화를 써야 할까? ]
   │
   ├─ [내가 풀 데이터인가? (서버 혼자 암복호화)] ───> 대칭키 (AES-256)
   │    └─ DB 개인정보, 서버 내부 파일 암호화
   │
   └─ [남과 안전하게 통신 / 신원을 증명해야 하는가?] ───> 비대칭키 (RSA / ECDSA)
        └─ HTTPS(TLS) 핸드셰이크, JWT 서명, 오픈 API 결제 연동

현대 웹의 해법: 하이브리드(Hybrid) 암호화 (HTTPS / TLS)#

웹 브라우저와 스프링 부트(또는 Nginx)가 HTTPS로 통신할 때는 “대칭키의 빠른 속도”와 “비대칭키의 안전한 키 배송”을 섞은 하이브리드 방식을 사용한다.

  1. 초기 연결 (Handshake - 비대칭키): 처음 연결할 때는 브라우저와 서버가 서로 신뢰할 수 있는 공유 키가 없으므로, 비대칭키(RSA/ECDSA)를 사용해 안전하게 인증서를 검증하고 통신용 임시 대칭키(세션키)를 하나 합의해 나눠 갖는다.
  2. 실제 데이터 전송 (대칭키): 핸드셰이크가 끝나면 실제 HTML, 이미지, JSON 같은 수 메가바이트의 본문 데이터는 속도가 빠른 대칭키(AES)로 암복호화하여 주고받는다.

5. 면접 대비 최종 정리#

Q2. 대칭키와 비대칭키 암호화의 차이점을 설명하고, 실무에서 각각 어떤 상황에 선택하시겠습니까?

  • 차이점: 대칭키는 암복호화 키가 동일하여 연산 속도가 매우 빠르지만 네트워크상에서 키를 안전하게 공유하기 어렵고, 비대칭키는 공개키와 개인키 쌍을 사용해 키 전달 문제와 전자서명(신원 증명)을 해결하지만 연산 비용이 크다는 트레이드오프가 있다.
  • 실무 적용:
    1. DB에 저장되는 주민번호나 계좌번호처럼 대량의 데이터를 서버 단독으로 암복호화해야 하는 구간에서는 CPU 부하와 저장 공간 낭비를 막기 위해 대칭키(AES-256)를 사용한다.
    2. 불특정 클라이언트와 통신하는 HTTPS(TLS)나 마이크로서비스 간 JWT 서명 검증처럼 상대방에게 비밀키를 노출하지 않고 안전하게 키를 교환하거나 신원을 증명해야 하는 구간에서는 비대칭키(RSA/ECDSA)를 활용하고, 이후 본문 데이터 전송은 대칭키로 처리하는 하이브리드 방식을 적용한다.
