1. 단방향 해싱 vs 양방향 암호화#

보안 이야기에서 관용적으로 “단방향 암호화"라는 표현을 자주 쓰지만, 컴퓨터공학(CS)에서는 복호화가 가능한 암호화(Encryption)와 원문 복원이 불가능한 해싱(Hashing)을 명확히 구분한다.

구분양방향 암호화 (AES-256, RSA 등)단방향 해싱 (SHA-256, bcrypt, Argon2 등)
동작 원리평문 ➔ (키로 잠금) ➔ 암호문 ➔ (키로 해제) ➔ 평문평문 ➔ (압축·변환) ➔ 고정 길이 해시값
복호화 여부가능 (비밀키 또는 개인키 보유 시)불가능 (정보 손실 발생, 비둘기집 원리)
주요 사용처주민등록번호, 계좌번호, 전화번호 등 원문 조회가 필요한 개인정보비밀번호, 파일 무결성 검증, 전자서명

왜 비밀번호는 무조건 “단방향 해시"여야 할까?#

“개발자 자신을 포함해 세상 그 누구도 사용자의 원래 비밀번호를 알아선 안 되기 때문이다.”

만약 DB가 통째로 유출되더라도 해커의 손에 들어가는 것은 복호화가 불가능한 해시값뿐이어야 안전하다. 로그인 검증 역시 원문을 복호화해 비교하는 것이 아니라, 사용자가 로그인할 때 입력한 비밀번호를 동일한 해시 함수에 통과시킨 뒤 DB에 저장된 해시값과 결과가 일치하는지만 비교한다.

2. 왜 MD5, SHA-256은 비밀번호 저장용으로 부적합할까?#

MD5, SHA-1, SHA-256 같은 범용 암호화 해시 함수는 원래 파일의 무결성 검사를 목적으로 설계되었지, 비밀번호를 보호하기 위해 만들어진 함수가 아니다. 과거에는 비밀번호 저장에도 SHA-256이나 MD5를 흔히 썼지만, 현재 기준으로는 치명적인 보안 취약점이 된다. 이유는 크게 두 가지다.

  1. 결정론적(Deterministic) 특성 ➔ 레인보우 테이블(Rainbow Table) 공격
    • 같은 입력을 넣으면 언제나 100% 같은 해시값이 나온다. (SHA-256("password123") = ef92b778...)
    • 공격자는 자주 쓰이는 비밀번호와 그 해시값을 미리 계산해 매핑해 둔 거대한 대조표(레인보우 테이블)를 만들어 두고, 유출된 해시값을 조회하는 것만으로 순식간에 원문을 찾아낸다.
  2. 지나치게 빠른 연산 속도 ➔ GPU 무차별 대입(Brute-Force) 공격
    • 범용 해시 함수는 수 GB짜리 파일의 변조 여부를 순식간에 검증하도록 설계되어 연산 비용이 극도로 낮다.
    • 최신 GPU 한 장만으로도 초당 수백억 회 이상의 SHA-256 연산이 가능하기 때문에, 8자리 영문+숫자 수준의 비밀번호는 몇 분 안에 전수 조사로 뚫릴 수 있다.

결국 일반적인 알고리즘은 ‘빠를수록’ 좋지만, 비밀번호 해시 함수는 ‘느릴수록’ 안전하다.

3. 해결책: 솔트(Salt)와 키 스트레칭(Key Stretching)#

[원문 비밀번호: "1234"]
        │
        ▼  1. Salt (사용자별 고유 난수 추가) ──▶ 레인보우 테이블 무력화
["1234" + "a8F!9k..."]
        │
        ▼  2. Hashing + Key Stretching (수만~수십만 회 반복 / 메모리 점유) ──▶ GPU 무차별 대입 지연
[최종 해시 문자열 (알고리즘 + Cost + Salt + Hash 결합 저장)]

안전한 비밀번호 저장 구조는 다음 세 가지 요소의 조합으로 완성된다.

  • 해시 함수 (Hashing): 원본 비밀번호를 알아볼 수 없는 고정 길이 문자열로 변환한다.
  • 솔트 (Salt): 사용자마다 무작위로 생성한 고유 난수 값을 비밀번호에 덧붙여 해싱한다. 똑같이 "1234"를 비밀번호로 쓰는 두 사용자라도 Salt가 다르면 최종 해시값이 완전히 달라지므로, 미리 만들어 둔 레인보우 테이블이 무용지물이 된다.
  • 키 스트레칭 (Key Stretching): 해싱 과정을 수만~수십만 번 반복하거나 대량의 메모리를 점유하게 만들어 일부러 연산 속도를 늦춘다. 이를 통해 공격자의 무차별 대입(Brute-Force) 공격 시간과 비용을 극단적으로 높인다.

개발자가 이 과정을 직접 반복문으로 구현하기보다는, 내부에 Salt 생성과 키 스트레칭 구조가 이미 표준화되어 있는 전용 키 파생 함수(KDF, Key Derivation Function)를 사용하는 것이 정석이다.

4. 표준 KDF 비교: PBKDF2 vs bcrypt vs Argon2id#

알고리즘내부 구조방어 강점주의사항 및 한계주 사용처
PBKDF2HMAC-SHA256 + Salt + 반복 횟수구현이 단순하고 검증 완료 (NIST/FIPS 표준)메모리 사용량이 적어 GPU/ASIC 병렬 공격에 상대적으로 취약금융권, 공공기관, 레거시 규제 준수 환경
bcryptBlowfish 기반 + Salt + costGPU 공격에 PBKDF2보다 강하고 생태계 지원이 가장 넓음비밀번호 최대 72바이트(Byte) 제한 (초과분 자동 절삭)범용 웹 서비스 표준
Argon2idSalt + 반복 횟수 + 대용량 RAM 강제 점유 + 병렬도메모리 하드(Memory-Hard) 특성으로 GPU/ASIC 대량 병렬 연산을 사실상 무력화서버 메모리(RAM) 설계 고려 필요OWASP 1순위 권장, 최신 신규 서비스
  • PBKDF2: 국내 보안 규정이나 금융권 가이드라인에서 널리 채택하는 표준 방식이다.
  • bcrypt: Spring Security의 BCryptPasswordEncoder를 비롯해 거의 모든 웹 프레임워크에서 기본으로 지원하는 가장 대중적인 선택지다. 단, 입력값이 72바이트를 넘어가면 뒷부분이 잘린다는 점에 유의해야 한다.
  • Argon2id: 연산마다 지정된 양의 RAM을 강제로 점유하게 만들어, 코어 수만 많고 코어당 메모리는 적은 GPU/ASIC 기반 크래킹 장비의 효율을 크게 떨어뜨린다.

5. 기존 해시 알고리즘 마이그레이션 전략#

서비스를 운영하다 보면 *“과거에 SHA-256으로 저장해 둔 회원 비밀번호를 bcrypt나 Argon2id로 바꾸려면 어떻게 해야 할까?"*라는 고민을 마주하게 된다.

비밀번호는 단방향 해시라서 원문을 복호화할 수 없기 때문에 DB 전체를 한 번에 새 알고리즘으로 변환할 수 없다. 따라서 현실적인 대안으로 두 가지 전략을 사용한다.

  1. 로그인 시점 점진적 마이그레이션 (Lazy Re-hashing)
    • DB에 {sha256}..., {bcrypt}..., {argon2}...처럼 알고리즘 접두사(Prefix)를 함께 저장해 관리한다. (Spring Security의 DelegatingPasswordEncoder가 지원하는 방식이다.)
    • 사용자가 로그인할 때 입력한 평문 비밀번호를 기존 {sha256} 방식으로 검증해 통과하면, 평문 비밀번호가 메모리에 살아 있는 그 순간에 즉시 {bcrypt} 또는 {argon2}로 다시 해싱해 DB를 덮어쓴다.
  2. 래핑(Wrapping) 마이그레이션
    • 장기 미접속 계정의 취약한 SHA-256 해시를 그대로 두기 위험할 때 사용하는 방식이다.
    • 기존의 SHA-256(pw) 결과값을 그대로 입력으로 삼아 bcrypt(SHA-256(pw))처럼 한 번 더 감싸서 배치 업데이트한다. 이후 사용자가 로그인할 때는 입력값을 먼저 SHA-256으로 해싱한 뒤 bcrypt로 검증하면 기존 계정 모두를 즉시 새 KDF로 보호할 수 있다.
