1. 세션(Session) vs JWT(Token) 한눈에 비교하기#

웹과 애플리케이션의 인증 아키텍처를 설계할 때 가장 먼저 마주하는 선택지는 서버가 클라이언트의 상태를 직접 기억할 것인가(Stateful), 아니면 토큰 자체에 증명서를 담아 서버는 검증만 할 것인가(Stateless)이다.

구분세션(Session) 기반JWT(Token) 기반
핵심 철학Stateful (서버가 상태를 기억)Stateless (서버는 검증만 수행, 상태 저장 X)
저장 위치서버 메모리 또는 Redis에 사용자 정보 저장클라이언트가 토큰을 보관 (서버 저장 X)
서버 확장성 (Scale-out)서버 증설 시 세션 동기화 필요 (복잡)서버가 수십 대로 늘어나도 즉시 검증 가능 (간단)
강제 로그아웃 / 제어즉시 가능 (서버 세션 저장소에서 삭제)원칙적으로 불가능 (만료 시점까지 유효)
적합한 환경단일 웹 서비스, 실시간 통제가 중요한 금융·관리자 시스템멀티 플랫폼(모바일 앱+웹), 마이크로서비스(MSA)

2. 세션(Session) 기반 인증의 동작 원리와 한계#

동작 흐름#

1. [클라이언트] ──(ID/PW 로그인 요청)──> [서버]
2. [서버] DB 검증 후, 서버 메모리(세션 저장소)에 "Session-123 = 1번 유저(홍길동)" 기록
3. [서버] ──(Set-Cookie: JSESSIONID=Session-123)──> [클라이언트]
4. [클라이언트] ──(Cookie: JSESSIONID=Session-123 포함하여 요청)──> [서버]
5. [서버] 세션 저장소에서 Session-123을 조회해 사용자 확인 후 응답

장점: 강력한 실시간 통제권#

보안 사고가 발생하거나 특정 계정을 즉시 차단해야 할 때, 서버의 세션 저장소에서 해당 세션 키 하나만 삭제하면 실시간으로 즉시 강제 로그아웃시킬 수 있다.

단점: 스케일 아웃(Scale-out) 시 발생하는 정합성 비용#

트래픽이 늘어나 로드 밸런서 뒤에 서버를 1번, 2번으로 증설(Scale-out)했다고 가정해 보자. 사용자가 1번 서버에서 로그인해 1번 서버 메모리에만 세션이 생성되었는데, 다음 요청이 2번 서버로 라우팅되면 2번 서버는 해당 세션을 알지 못해 로그인이 풀리는 문제가 발생한다.

이를 해결하려면 특정 사용자의 요청을 특정 서버로만 고정하는 Sticky Session을 쓰거나, Redis 같은 별도의 중앙 집중형 인메모리 세션 저장소(Session Clustering)를 구축해야 하므로 추가적인 인프라 및 네트워크 비용이 수반된다.

3. JWT(JSON Web Token)의 동작 원리와 내부 구조#

동작 흐름#

1. [클라이언트] ──(ID/PW 로그인 요청)──> [서버]
2. [서버] DB 검증 후, 서버 비밀키(Secret Key)로 전자서명한 JWT 발급
3. [서버] ──(JWT 반환)──> [클라이언트]
4. [클라이언트] ──(Authorization: Bearer <JWT> 헤더에 첨부)──> [서버]
5. [서버] DB나 메모리 조회 없이, 비밀키를 통한 서명(Signature) 검증만으로 즉시 승인

JWT의 내부 구조 (Header.Payload.Signature)#

JWT는 점(.)을 기준으로 세 영역으로 나뉘며, 각 영역은 Base64 URL 방식으로 인코딩된다.

[Header] . [Payload] . [Signature]

1. Header (헤더)
   - 토큰 타입(JWT)과 서명에 사용한 해싱 알고리즘(HMAC SHA256, RSA 등) 명시

2. Payload (페이로드 / 클레임)
   - 실제 전달할 데이터 (유저 식별자 PK, 권한 Role, 만료 시간 exp 등)
   - 암호화(Encryption)가 아니라 단순 Base64 인코딩이므로 누구나 디코딩해 내용을 볼 수 있음

3. Signature (서명)
   - (Header + Payload + 서버만 알고 있는 Secret Key)를 조합해 해싱한 전자 인감도장
   - 누군가 중간에서 Payload의 권한이나 ID를 단 한 글자라도 변조하면 서명값이 달라져 검증 단계에서 즉시 거부됨

Q. Payload는 Base64 디코딩만 하면 누구나 내용을 볼 수 있는데 왜 안전하며, 어떤 정보를 담으면 안 될까?

JWT의 목적은 데이터를 숨기는 기밀성(Confidentiality)이 아니라, 데이터가 위변조되지 않았음을 보증하는 무결성(Integrity)에 있다. 공격자가 Payload를 읽을 수는 있어도 서버의 비밀키(Secret Key)를 모르는 이상 유효한 서명(Signature)을 만들어낼 수 없으므로 내용을 조작할 수 없다. 단, 누구나 열람할 수 있는 영역이므로 비밀번호, 주민등록번호, 계좌번호, 서버 시크릿 등 민감한 개인정보는 절대 Payload에 담아서는 안 되며, 최소한의 식별자(유저 ID, Role 등)와 만료 시간만 담아야 한다.

JWT의 장단점#

  • 장점 (높은 확장성): 서버가 상태를 저장하지 않으므로 서버가 100대로 늘어나거나 MSA 환경에서 여러 서비스로 쪼개져도 동일한 비밀키(또는 공개키)만 공유하면 별도의 저장소 조회 없이 CPU 연산만으로 즉시 인증을 마칠 수 있다.
  • 치명적인 단점 (즉시 회수 불가): 한 번 발급되어 클라이언트에 넘어간 토큰은 서버가 제어할 수 없다. 만약 토큰이 탈취되면 해당 토큰의 만료 시간(exp)이 끝날 때까지 해커의 요청을 막을 방법이 없다.

4. JWT의 한계를 보완하는 실무 설계 전략#

전략 1: Access Token + Refresh Token 분리와 RTR(Refresh Token Rotation)#

단일 토큰의 탈취 위험을 줄이기 위해 실무에서는 역할과 수명이 다른 두 개의 토큰으로 생명주기를 분리한다.

  • Access Token (수명 15분~30분): API 통신에 매번 사용되는 토큰이다. 완전한 Stateless로 운영하되, 탈취되더라도 피해 시간을 최소화하기 위해 유효기간을 아주 짧게 설정한다.
  • Refresh Token (수명 1~2주): Access Token이 만료되었을 때 새로운 Access Token을 재발급받는 용도로만 사용한다. 탈취 시 강제 로그아웃 통제권을 확보하기 위해 Refresh Token만 서버의 Redis에 저장하는 하이브리드 전략을 취한다.
  • RTR (Refresh Token Rotation): 여기서 한 단계 더 나아가, Access Token을 재발급할 때마다 기존 Refresh Token을 즉시 폐기하고 새로운 Refresh Token을 함께 발급(1회용화) 한다. 만약 이미 사용되어 폐기된 Refresh Token으로 재발급 요청이 들어오면 서버는 이를 토큰 탈취로 간주하고 Redis에서 해당 사용자의 모든 세션을 즉시 만료시켜 공격자를 차단한다.

전략 2: 브라우저 어디에 토큰을 보관할 것인가? (XSS vs CSRF 방어)#

프론트엔드(Vue, React 등)와 백엔드가 협업할 때 가장 중요하게 결정해야 하는 보안 포인트가 바로 클라이언트 측 토큰 저장 위치다.

  1. localStorage / sessionStorage 단독 저장의 위험성: 자바스크립트 코드(localStorage.getItem)로 언제든 읽을 수 있으므로, 게시판이나 입력창을 통해 악성 스크립트가 실행되는 XSS(Cross-Site Scripting) 공격에 노출되면 토큰이 그대로 탈취된다.
  2. HttpOnly 쿠키 단독 저장 시 고려사항: 브라우저에서 자바스크립트(document.cookie)의 접근을 원천 차단하므로 XSS로부터는 안전하다. 하지만 브라우저가 해당 도메인으로 요청을 보낼 때 쿠키를 자동으로 첨부하므로, 다른 악성 사이트에서 위조 요청을 유도하는 CSRF(Cross-Site Request Forgery) 공격에 대한 방어(SameSite 옵션 등)가 반드시 동반되어야 한다.

XSS와 CSRF를 모두 방어하는 권장 표준 아키텍처#

현재 실무에서 가장 널리 권장되는 표준 조합은 Access Token은 자바스크립트 인메모리 변수에, Refresh Token은 HttpOnly + Secure + SameSite 쿠키에 분리 저장하는 방식이다.

┌─────────────────┬────────────────────────────────────────────────────────┐
│ Access Token    │ 자바스크립트 메모리 (React State / Pinia / Vuex 변수)  │
├─────────────────┼────────────────────────────────────────────────────────┤
│ Refresh Token   │ HttpOnly + Secure + SameSite=Strict (또는 Lax) 쿠키    │
└─────────────────┴────────────────────────────────────────────────────────┘
  • Access Token ➔ 자바스크립트 메모리(변수)에 저장:
    • localStorage나 쿠키 같은 영구 저장소에 남지 않고 브라우저 메모리(변수)에만 존재하므로 XSS 스크립트가 로컬 스토리지를 뒤져도 털어갈 토큰이 없다.
    • 또한 API 호출 시 쿠키처럼 자동 전송되지 않고 코드에서 직접 Authorization: Bearer 헤더에 실어 보내므로 CSRF 공격으로부터도 안전하다. (새로고침 시 메모리가 초기화되면 쿠키에 있는 Refresh Token으로 조용히 재발급(Silent Refresh)받는다.)
  • Refresh Token ➔ HttpOnly + Secure + SameSite 쿠키에 저장:
    • HttpOnly 속성으로 자바스크립트의 쿠키 접근을 차단해 XSS 공격으로 Refresh Token이 탈취되는 것을 원천 봉쇄한다.
    • Secure 속성으로 오직 HTTPS 암호화 통신에서만 전송되도록 강제한다.
    • SameSite=Strict (또는 Lax) 속성을 설정해 외부 사이트에서 위조된 크로스 사이트 요청에는 쿠키가 전송되지 않도록 막아 CSRF 공격까지 방어한다.

5. 핵심 요약: 실무에서는 어떤 기준으로 선택할까?#

  1. 세션 vs JWT의 본질적 차이: 서버가 상태를 유지하며 즉각적인 통제권을 갖느냐(Stateful), 아니면 토큰 서명 검증만으로 상태를 위임해 수평 확장성을 극대화하느냐(Stateless)의 트레이드오프다.
  2. 도메인별 선택 기준:
    • 금융권이나 사내 어드민처럼 실시간 세션 통제와 즉각적인 강제 만료가 최우선인 환경에서는 세션(Redis 클러스터링 기반) 방식이 적합하다.
    • 모바일 네이티브 앱과 웹을 동시에 지원해야 하거나, 트래픽이 크고 서비스가 분리된 MSA / RESTful API 환경에서는 Access Token(인메모리, 단기) + Refresh Token(Redis & HttpOnly 쿠키, RTR 적용)을 결합한 하이브리드 JWT 아키텍처가 적합하다.
