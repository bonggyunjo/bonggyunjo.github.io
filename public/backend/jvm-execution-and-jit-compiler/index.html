1. 전체 실행 흐름 한눈에 보기#

자바 소스코드(.java)가 작성되어 실제 CPU에서 기계어로 실행되기까지의 핵심 흐름을 도식화하면 다음과 같다.

[Java 코드] ➔ javac 컴파일 ➔ [.class 바이트코드] ➔ [클래스 로더] ➔ [인터프리터로 즉시 기동]
                                                                        │
                                                (자주 쓰는 코드 감지! 핫스팟 임계치 도달)
                                                                        ▼
                                                [JIT 컴파일러가 네이티브 기계어로 번역]
                                                                        │
                                                                        ▼
                                                [Code Cache에 저장 ➔ 이후 CPU 직행 초고속 실행]

JVM은 .class 바이트코드를 클래스 로더를 통해 메모리에 올린 뒤, 초기에는 인터프리터(Interpreter)로 빠르게 한 줄씩 해석하여 실행한다. 이후 자주 실행되어 임계치(Hotspot)를 넘은 코드 블록을 JIT(Just-In-Time) 컴파일러가 직접 네이티브 기계어로 번역해 Code Cache에 저장함으로써, 이후 호출부터는 번역 과정 없이 C/C++에 준하는 속도로 실행한다.

2. 왜 자바는 컴파일러와 인터프리터를 모두 사용할까?#

흔히 자바를 가리켜 컴파일 언어이면서 동시에 인터프리터 언어라고 부른다. 얼핏 상충해 보이는 두 방식을 함께 사용하는 이유는 플랫폼 독립성(이식성)과 실행 성능이라는 두 가지 목표를 모두 잡기 위해서다.

  1. 1차 컴파일 (javac) — 플랫폼 독립성 확보: javac 컴파일러는 자바 소스코드를 특정 OS나 CPU에 종속된 기계어가 아닌, 모든 JVM이 공통으로 이해할 수 있는 중간 단계의 바이트코드(.class)로 변환한다. 덕분에 한 번 빌드한 파일은 Windows, Linux, macOS 어디서든 동일하게 실행할 수 있다.
  2. 인터프리터 실행 — 빠른 초기 기동: 애플리케이션이 시작될 때 전체 바이트코드를 전부 기계어로 번역하려면 기동 시간이 길어진다. 따라서 JVM 실행 엔진은 우선 인터프리터를 통해 바이트코드를 한 줄씩 즉시 해석하여 실행 지연 없이 빠르게 서버를 띄운다.
  3. 2차 컴파일 (JIT Compiler) — 반복 실행 구간의 성능 극대화: 인터프리터만 사용하면 똑같은 메서드가 수만 번 호출될 때마다 매번 똑같은 바이트코드를 다시 번역해야 하는 비효율이 발생한다. 이를 해결하기 위해 자주 실행되는 핵심 구간을 통째로 네이티브 기계어로 번역해 두는 JIT 컴파일러가 함께 동작한다.

비유하자면 JVM은 동시 통역사(인터프리터)와 전문 번역가(JIT 컴파일러)를 함께 둔 구조다. 처음 문서를 읽을 때는 동시 통역사가 한 문장씩 바로 통역해 시작 속도를 높이고, 특정 챕터가 수만 번 반복해서 읽히는 핵심 구간(Hotspot)임이 확인되면 전문 번역가가 아예 완성된 번역본(네이티브 기계어)을 인쇄해 책장(Code Cache)에 꽂아두고 그다음부터는 통역 없이 바로 읽는 방식이다.

3. 단계별 상세 구동 메커니즘#

1) 클래스 로더(Class Loader)의 3단계#

.class 파일이 JVM 메모리(Runtime Data Area)에 올라오기까지 클래스 로더는 다음 세 단계를 거친다.

  • Loading (로딩): .class 바이트코드 파일을 읽어 JVM 메모리의 메서드 영역(Method Area)에 적재한다.
  • Linking (링킹): 로드된 바이트코드를 실행 가능한 상태로 연결하는 단계로, 내부적으로 다시 3단계로 나뉜다.
    1. Verification (검증): 읽어들인 바이트코드가 자바 및 JVM 명세를 준수하는지, 보안상 위험하거나 깨진 코드는 없는지 검증한다.
    2. Preparation (준비): 클래스의 static 변수들을 위한 메모리 공간을 할당하고, 타입별 기본값(0, null, false 등)으로 초기화한다.
    3. Resolution (해석): 클래스의 런타임 상수 풀(Runtime Constant Pool)에 있는 심볼릭 참조(Symbolic Reference, 문자열 이름 기반 참조)를 실제 메모리 주소를 가리키는 직접 참조(Direct Reference)로 교체한다.
  • Initialization (초기화): Preparation 단계에서 기본값으로만 채워두었던 static 변수들에 코드에 명시된 실제 값을 대입하고, static 초기화 블록(static { ... })을 실행한다.

2) 핫스팟(Hotspot) 프로파일링과 JIT 컴파일#

클래스 로딩이 끝나고 실행 엔진(Execution Engine)이 코드를 실행하기 시작하면 내부 프로파일러가 함께 동작한다.

  1. 호출 및 루프 카운팅: JVM 내부 카운터가 특정 메서드가 호출된 횟수(Invocation Counter)와 메서드 내 루프가 반복된 횟수(Backedge Counter)를 지속적으로 기록한다.
  2. 핫스팟 감지: 카운터 수치가 JVM에 설정된 임계치를 넘어서는 순간, 해당 코드를 성능에 결정적인 영향을 미치는 핫스팟(Hotspot) 으로 판단한다.
  3. 네이티브 기계어 번역 (C1 / C2 컴파일러): 감지된 바이트코드 블록을 JIT 컴파일러(빠른 컴파일을 담당하는 C1 클라이언트 컴파일러와 고도화된 최적화를 수행하는 C2 서버 컴파일러)가 현재 서버 CPU 아키텍처(x86-64, ARM 등)에 맞는 네이티브 어셈블리 기계어로 번역한다.
  4. Code Cache 적재: 번역된 기계어는 JVM 메모리의 Code Cache 영역에 저장되며, 이후 해당 메서드가 호출되면 인터프리터를 거치지 않고 Code Cache의 기계어를 CPU가 직접 실행한다.

4. 코드로 보는 인터프리터 단독 실행 vs JIT 컴파일 실행#

수억 번 반복되는 연산 루프에서 인터프리터만 동작할 때와 JIT 컴파일러가 개입할 때의 차이는 다음과 같다.

인터프리터 모드만 동작할 때 (-Xint 옵션)#

// JVM 옵션으로 JIT를 끄고 인터프리터만 강제한 경우 (-Xint)
// 매 반복마다 바이트코드(iload, iadd 등)를 한 줄씩 CPU 명령어로 해석하여 실행
for (int i = 0; i < 100_000_000; i++) {
    sum += compute(i);
}
// 1억 번 반복 시 1억 번의 바이트코드 해석 오버헤드가 그대로 누적됨 (실행 시간 약 3.8초)

JIT 컴파일러 활성화 시 (HotSpot JVM 기본 동작)#

// HotSpot JVM 기본 실행 시
for (int i = 0; i < 100_000_000; i++) {
    sum += compute(i); // 일정 임계치(예: 약 10,000회) 도달 시점에 핫스팟으로 감지
}
// JIT 컴파일러가 compute 메서드와 루프 구간을 통째로 네이티브 기계어로 번역하여 Code Cache에 캐싱
// 이후 반복부터는 바이트코드 해석 없이 CPU 레지스터 직접 연산으로 직행 (실행 시간 약 0.1초)

5. 실무 운영 포인트: 왜 신규 배포 직후에 JVM Warm-up이 필요할까?#

이 구동 메커니즘을 이해하면 실무에서 서버를 새로 배포하거나 스케일 아웃(Scale-out)한 직후 왜 일시적으로 응답 속도가 튀고 CPU 사용률이 치솟는지 명확히 설명할 수 있다.

  • 배포 직후의 상태 (Cold State): 스프링 부트 서버가 막 부팅된 시점에는 컨트롤러, 서비스, 직렬화 로직 등 대부분의 핵심 메서드가 아직 임계치에 도달하지 않아 인터프리터 모드로 실행된다. 게다가 트래픽이 몰리면서 수많은 메서드가 동시에 JIT 컴파일 대상이 되면, 백그라운드에서 JIT 컴파일 스레드가 바쁘게 돌아가며 CPU 자원을 추가로 소모한다.
  • 정상 궤도 진입 (Warmed-up State): 일정량의 요청을 처리하고 나면 주요 비즈니스 로직과 프레임워크 내부 코드들이 모두 JIT 컴파일을 마치고 Code Cache에 기계어로 안착하여 빠르고 안정적인 응답 속도를 낸다.

따라서 대규모 트래픽을 처리하는 환경에서는 신규 인스턴스를 띄운 직후 곧바로 프로덕션 트래픽의 100%를 쏟아붓지 않고, 부팅 직후 내부적으로 더미 요청을 흘려보내 주요 경로의 JIT 컴파일을 미리 유도하는 JVM Warm-up 과정을 거치거나 카나리/점진적 가중치 배포를 적용해 초기 응답 지연(Timeout)을 예방한다.

6. 핵심 요약#

  1. 이중 실행 구조: 자바는 javac를 통해 플랫폼 독립적인 바이트코드(.class)를 만들고, JVM 내부에서 인터프리터(빠른 초기 기동)와 JIT 컴파일러(반복 구간 네이티브 기계어 번역)를 결합해 이식성과 성능을 동시에 달성한다.
  2. 클래스 로더 3단계: Loading(메모리 적재) ➔ Linking(바이트코드 검증 Verification, static 기본값 할당 Preparation, 심볼릭 참조를 실제 주소로 변환 Resolution) ➔ Initialization(static 실제 값 대입 및 초기화 블록 실행) 순서로 진행된다.
  3. Code Cache와 Warm-up: 자주 호출되는 핫스팟 코드는 JIT 컴파일러를 거쳐 Code Cache에 기계어로 저장되며, 배포 직후 이 과정이 완료되기 전까지 발생하는 초기 지연과 CPU 부하를 줄이기 위해 JVM Warm-up 전략이 활용된다.
