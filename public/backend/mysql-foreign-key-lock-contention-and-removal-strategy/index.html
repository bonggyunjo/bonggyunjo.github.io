1. 외래키(Foreign Key)와 데이터베이스 락(Lock)의 개념#

외래키(Foreign Key)란?#

외래키는 두 테이블 간의 부모-자식 관계를 연결하고 참조 무결성(Referential Integrity)을 강제하는 제약조건이다.

예를 들어 OrderItem(주문상품) 테이블의 product_id가 Product(상품) 테이블의 id를 참조하도록 외래키를 걸어두면, 존재하지 않는 상품 ID로 주문이 들어오거나 주문이 연결된 상품이 함부로 삭제되는 상황을 DB 엔진 차원에서 막아준다.

락(Lock)이란?#

데이터베이스의 락(Lock, 잠금)은 여러 요청이 동시에 같은 데이터를 건드릴 때 데이터가 꼬이지 않도록 줄을 세우는 장치다.

예를 들어 재고가 1개 남은 상품을 사용자 A와 B가 정확히 같은 순간에 결제하려 할 때, 잠금 장치가 없다면 두 요청 모두 “재고 1개 있네!” 하고 통과시켜 버려 재고가 -1개가 되는 사고가 발생한다. 이를 막기 위해 데이터를 읽거나 쓰는 동안 다른 트랜잭션의 접근을 통제하는 것이 락이다.

2. S-Lock(공유 락)과 X-Lock(배타 락)#

MySQL(InnoDB)의 잠금은 크게 읽기용 잠금인 S-Lock과 쓰기용 잠금인 X-Lock으로 나뉜다.

1) S-Lock (Shared Lock, 공유 락 / 읽기 락)#

  • 목적: 리소스를 여러 트랜잭션이 동시에 읽는 것은 허용하되, 읽는 도중 데이터가 변경되는 것은 차단한다.
  • 다른 트랜잭션의 S-Lock: 허용 (여러 트랜잭션이 동시에 같은 데이터를 읽을 수 있다.)
  • 다른 트랜잭션의 X-Lock: 차단 (읽는 도중 다른 트랜잭션이 UPDATE, DELETE 하는 것을 막는다.)
  • 예시: SELECT ... FOR SHARE

2) X-Lock (Exclusive Lock, 배타 락 / 쓰기 락)#

  • 목적: 데이터를 수정하거나 삭제하는 동안 다른 트랜잭션의 접근을 완전히 막아 데이터 무결성을 지킨다.
  • 다른 트랜잭션의 S-Lock: 차단
  • 다른 트랜잭션의 X-Lock: 차단
  • 예시: INSERT, UPDATE, DELETE, SELECT ... FOR UPDATE
현재 걸린 락 \ 요청한 락S-Lock (공유 락)X-Lock (배타 락)
S-Lock (공유 락)허용 (함께 읽기 가능)대기(차단)
X-Lock (배타 락)대기(차단)대기(차단)

정리하면 S-Lock은 다른 트랜잭션의 S-Lock 획득은 허용하지만 X-Lock(UPDATE, DELETE)은 막고, X-Lock은 다른 트랜잭션의 S-Lock과 X-Lock 획득을 모두 막는다.

3. 왜 외래키(FK)가 대규모 트래픽에서 락 경합을 유발할까?#

MySQL(InnoDB)에서 외래키가 대규모 트래픽 환경의 병목과 데드락을 유발하는 핵심 원인은 데이터 무결성을 지키기 위해 DB 엔진이 내부적으로 거는 ‘암묵적 락(Implicit Lock)’ 때문이다.

자식 테이블(OrderItem)에 데이터를 INSERT하거나 외래키 컬럼을 UPDATE할 때, InnoDB는 *“내가 참조하려는 부모(Product)가 방금 누군가에게 삭제되거나 변경되고 있지 않은가?"*를 보장하기 위해 부모 테이블의 해당 레코드에 암묵적으로 S-Lock을 건다.

[트랜잭션 A: 주문 상품 등록]
  └─ OrderItem INSERT (product_id = 10)
  └─ InnoDB가 참조 무결성 확인을 위해 부모 Product(id = 10) 행에 암묵적 S-Lock 획득!

[트랜잭션 B: 상품 정보/재고 수정]
  └─ Product UPDATE (id = 10) ➔ X-Lock 필요!
  └─ 트랜잭션 A가 걸어둔 S-Lock 때문에 대기(Lock Wait) 발생!

평소 트래픽이 적을 때는 거의 티가 나지 않지만, 인기 상품 하나에 수백~수천 건의 주문(OrderItem INSERT)과 재고/상태 업데이트(Product UPDATE)가 동시에 몰리면 부모 레코드 하나의 S-Lock과 X-Lock을 두고 수많은 트랜잭션이 줄을 서면서 심각한 쓰기 락 경합과 데드락(Deadlock)이 발생한다.

이 때문에 실무에서 대규모 트래픽을 다루는 서비스들은 논리적인 관계는 유지하되 물리적인 DB 외래키(FOREIGN KEY) 제약조건은 제거하고 인덱스와 애플리케이션 로직으로 대체하는 전략을 자주 선택한다.

4. 외래키(FK)를 제거했을 때의 부작용과 애플리케이션 보완 전략#

발생할 수 있는 부작용#

DB 차원의 외래키 제약조건을 없애면 락 경합에서는 자유로워지지만, 부모-자식 참조 무결성을 DB가 자동으로 막아주지 않기 때문에 부모 데이터가 삭제되었는데 자식 데이터가 그대로 남아있는 고아 데이터(Orphan Data)나 참조 불일치가 발생할 수 있다.

애플리케이션 계층의 3가지 보완 전략#

  1. 트랜잭션 내 연관 데이터 검증 철저히 수행
    • 자식 데이터를 생성·수정하기 전, 동일한 트랜잭션 범위 안에서 부모 데이터가 실제로 존재하는지 애플리케이션 로직(repository.existsById(...) 등)으로 먼저 검증한다.
  2. 부모 데이터 삭제 시 논리적 삭제(Soft Delete) 적용
    • 부모 레코드를 DELETE 쿼리로 물리 삭제하면 기존 자식 데이터들의 참조 대상이 사라지게 된다. 대신 deleted_at이나 is_deleted 플래그를 갱신하는 Soft Delete를 적용해 과거 주문·이력 데이터의 참조 무결성을 안전하게 보존한다.
  3. 배치 프로세스 및 정합성 검증 스케줄러 운영
    • 분산 환경이나 예외 상황으로 인해 간헐적으로 발생할 수 있는 고아 데이터를 막기 위해, 주기적으로 도는 배치(Batch) 작업이나 정합성 검증 스케줄러를 두어 연결이 끊어진 데이터를 탐지하고 정리한다.
