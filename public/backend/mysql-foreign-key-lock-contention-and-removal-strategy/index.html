1. 외래키(Foreign Key)와 데이터베이스 락(Lock)의 개념#

외래키(Foreign Key)란?#

외래키는 두 테이블 간의 부모-자식 관계를 연결하고 참조 무결성(Referential Integrity)을 강제하는 제약조건이다.

예를 들어 OrderItem(주문상품) 테이블의 product_id가 Product(상품) 테이블의 id를 참조하도록 외래키를 걸어두면, 존재하지 않는 상품 ID로 주문이 들어오거나 주문이 연결된 상품이 함부로 삭제되는 상황을 DB 엔진 차원에서 막아준다.

락(Lock)이란?#

데이터베이스의 락(Lock, 잠금)은 여러 요청이 동시에 같은 데이터를 건드릴 때 데이터가 꼬이지 않도록 줄을 세우는 동시성 제어 장치다.

예를 들어 재고가 1개 남은 상품을 사용자 A와 B가 정확히 같은 순간에 결제하려 할 때, 잠금 장치가 없다면 두 요청 모두 “재고 1개 있네!” 하고 통과시켜 버려 재고가 -1개가 되는 사고가 발생한다. 이를 막기 위해 InnoDB는 테이블 전체가 아니라 특정 행(Row) 단위에 잠금을 거는 방식을 기본으로 사용하며, 이 행 잠금이 바로 S-Lock과 X-Lock이다.

2. S-Lock(공유 락)과 X-Lock(배타 락)#

1) S-Lock (Shared Lock, 공유 락 / 읽기 락)#

  • 동작 방식: 데이터를 ‘읽기’ 위해 거는 락이다. 트랜잭션 A가 특정 행에 S-Lock을 걸면, 트랜잭션 B도 같은 행에 S-Lock을 걸고 데이터를 함께 읽을 수 있다.
  • 제약 사항: S-Lock이 하나라도 걸려 있는 동안에는 다른 트랜잭션이 해당 행을 수정하거나 삭제(X-Lock 획득)할 수 없으며, S-Lock이 해제될 때까지 대기해야 한다.
-- MySQL 8.0 이상 권장 문법
SELECT * FROM accounts WHERE id = 1 FOR SHARE;

-- 구버전 문법 (하위 호환)
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;

주의: 일반적인 SELECT * FROM accounts WHERE id = 1; 쿼리는 S-Lock을 걸지 않는다. InnoDB는 MVCC(다중 버전 동시성 제어)를 통해 락 없이 스냅샷을 읽어오기 때문이다. S-Lock은 위처럼 FOR SHARE를 명시하거나, 뒤에서 살펴볼 외래키 제약조건 검사 같은 내부 동작 시에 걸린다.

2) X-Lock (Exclusive Lock, 배타 락 / 쓰기 락)#

  • 동작 방식: 데이터를 ‘수정(쓰기) 및 삭제’하기 위해 독점적으로 거는 락이다. 트랜잭션 A가 특정 행에 X-Lock을 걸면, COMMIT 또는 ROLLBACK으로 종료될 때까지 다른 트랜잭션은 해당 행에 S-Lock도, X-Lock도 걸 수 없다.
  • 제약 사항: 다른 트랜잭션이 같은 행을 수정하려 하거나(X-Lock 요청), FOR SHARE로 읽으려 하면(S-Lock 요청) 모두 대기 상태(Lock Wait)에 빠진다.
-- 쓰기 작업 시 자동으로 해당 행에 X-Lock 획득
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
DELETE FROM accounts WHERE id = 1;

-- 조회 단계에서 미리 수정 의도를 밝히고 X-Lock을 걸고 싶을 때
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

3) S-Lock vs X-Lock 호환성 매트릭스#

현재 걸린 락 \ 요청한 락S-Lock (공유 락) 요청X-Lock (배타 락) 요청
S-Lock (공유 락) 보유 중호환 (즉시 획득)충돌 (대기)
X-Lock (배타 락) 보유 중충돌 (대기)충돌 (대기)

4) 실무에서 꼭 알아야 할 락 동작 포인트 3가지#

  1. 일반 SELECT는 X-Lock이 걸려 있어도 멈추지 않는다: 트랜잭션 A가 UPDATE로 X-Lock을 잡고 있더라도, 트랜잭션 B가 일반 SELECT를 실행하면 대기하지 않고 MVCC 스냅샷(변경 전 데이터)을 즉시 읽어온다. 대기하는 경우는 B가 FOR SHARE나 FOR UPDATE를 명시했을 때다.
  2. InnoDB의 락은 ‘레코드’가 아니라 ‘인덱스’에 걸린다: WHERE 조건에 인덱스가 걸린 컬럼을 사용하면 해당 행의 인덱스만 잠근다. 하지만 인덱스가 없는 컬럼으로 UPDATE를 실행하면 테이블 전체를 스캔하면서 모든 행에 X-Lock이 걸려 심각한 성능 저하가 발생할 수 있다.
  3. S-Lock에서 X-Lock으로의 업그레이드와 데드락: 트랜잭션 A와 B가 동시에 같은 행에 S-Lock을 획득한 상태에서 둘 다 해당 행을 수정하려고 X-Lock을 요청하면, 서로의 S-Lock이 풀리기를 영원히 기다리는 데드락(Deadlock)에 빠진다. 따라서 조회 후 곧바로 수정할 데이터라면 처음부터 SELECT ... FOR UPDATE(X-Lock)를 사용하는 것이 안전하다.

3. 실전 시나리오: 재고 1개 남은 상품을 A가 결제 중이면 B에게는 어떻게 보일까?#

여기서 자주 헷갈리는 질문이 하나 있다. “재고가 1개 남은 상품을 A 고객이 보고 결제창까지 넘어갔을 때, 다른 위치에 있는 B 고객 화면에는 재고가 0개로 보일까, 1개로 보일까?”

결론부터 말하면, 일반적인 쇼핑몰 구조에서는 B 고객에게도 여전히 재고가 1개로 보인다. 여기에는 아키텍처 이유와 InnoDB(MVCC)의 원리 두 가지가 맞물려 있다.

  1. 결제창에 머문다고 해서 X-Lock을 잡고 있지 않는다
    • A가 결제창에서 카드 번호를 입력하거나 본인 인증을 하는 수십 초 동안 DB 트랜잭션을 열어두고 X-Lock을 잡고 있는 구조는 쓰지 않는다. 그렇게 하면 A가 결제창만 켜놓고 자리를 비웠을 때 DB 락이 몇 분씩 묶여 시스템 전체가 마비된다.
    • 실제 DB의 UPDATE(재고 차감)는 A가 최종 ‘결제 완료’ 버튼을 눌러 승인이 떨어지는 찰나의 순간(수 밀리초)에 실행되고 즉시 COMMIT 된다.
  2. 설령 A가 딱 UPDATE 중(X-Lock 보유, COMMIT 전)이어도 B에게는 1개로 보인다
    • A가 결제 버튼을 눌러 DB에서 재고를 1 -> 0으로 바꾸는 UPDATE를 실행 중인 찰나에 B가 상품 페이지를 조회(SELECT)해도, InnoDB의 일반 SELECT는 X-Lock에 걸려 대기하지 않고 MVCC를 통해 수정 직전의 과거 스냅샷(1개)을 그대로 읽어온다.
    • 즉, A의 트랜잭션이 최종 COMMIT 되어야만 그 이후 조회하는 B에게 비로소 0개(품절)로 보인다.
  3. 그럼 B도 1개인 줄 알고 동시에 결제 버튼을 누르면?
    • 바로 이 순간에 X-Lock이 중복 결제를 막아준다.
    • 0.001초 먼저 도착한 A가 해당 상품 행의 X-Lock을 획득하고 재고를 1 -> 0으로 차감한 뒤 COMMIT 한다.
    • 간발의 차로 늦은 B는 X-Lock 충돌로 잠시 대기(Lock Wait)하다가, A가 COMMIT 하며 락을 풀어주면 그제야 방금 갱신된 최신 재고(0개)를 확인하고 “재고가 부족합니다” 안내를 띄우며 안전하게 차단된다.

예외: 콘서트 티켓팅처럼 결제창에 들어가자마자 0개로 보이는 서비스는? 티켓팅이나 항공권 예매 역시 결제 끝날 때까지 DB 락(X-Lock)을 쥐고 있는 것은 아니다. 대신 임시 선점(Reservation) 방식을 쓴다. A가 결제창에 진입하는 순간 DB에 재고를 1개 빼거나 상태를 RESERVED로 UPDATE 한 뒤 곧바로 COMMIT 해서 락을 풀어버린다. 이미 COMMIT이 끝났기 때문에 B에게는 즉시 0개로 보이며, 만약 A가 제한 시간(예: 5분) 안에 결제를 완료하지 않고 나가면 스케줄러나 타임아웃 로직이 선점을 취소하고 재고를 다시 1개로 복구한다.

4. 왜 외래키(FK)가 대규모 트래픽에서 락 경합을 유발할까?#

이제 S-Lock과 X-Lock의 동작을 바탕으로 다시 외래키 문제로 돌아와 보자. MySQL(InnoDB)에서 외래키가 대규모 트래픽 환경의 병목과 데드락을 유발하는 핵심 원인은 데이터 무결성을 지키기 위해 DB 엔진이 내부적으로 거는 ‘암묵적 락(Implicit Lock)’ 때문이다.

자식 테이블(OrderItem)에 데이터를 INSERT하거나 외래키 컬럼을 UPDATE할 때, InnoDB는 *“내가 참조하려는 부모(Product)가 방금 누군가에게 삭제되거나 변경되고 있지 않은가?"*를 보장하기 위해 부모 테이블의 해당 레코드에 암묵적으로 S-Lock을 건다.

[트랜잭션 A: 주문 상품 등록]
  └─ OrderItem INSERT (product_id = 10)
  └─ InnoDB가 참조 무결성 확인을 위해 부모 Product(id = 10) 행에 암묵적 S-Lock 획득!

[트랜잭션 B: 상품 정보/재고 수정]
  └─ Product UPDATE (id = 10) ➔ X-Lock 필요!
  └─ 트랜잭션 A가 걸어둔 S-Lock 때문에 대기(Lock Wait) 발생!

평소 트래픽이 적을 때는 거의 티가 나지 않지만, 인기 상품 하나에 수백~수천 건의 주문(OrderItem INSERT)과 재고/상태 업데이트(Product UPDATE)가 동시에 몰리면 부모 레코드 하나의 S-Lock과 X-Lock을 두고 수많은 트랜잭션이 줄을 서면서 심각한 쓰기 락 경합과 데드락(Deadlock)이 발생한다.

이 때문에 실무에서 대규모 트래픽을 다루는 서비스들은 논리적인 관계는 유지하되 물리적인 DB 외래키(FOREIGN KEY) 제약조건은 제거하고 인덱스와 애플리케이션 로직으로 대체하는 전략을 자주 선택한다.

5. 외래키(FK)를 제거했을 때의 부작용과 애플리케이션 보완 전략#

발생할 수 있는 부작용#

DB 차원의 외래키 제약조건을 없애면 락 경합에서는 자유로워지지만, 부모-자식 참조 무결성을 DB가 자동으로 막아주지 않기 때문에 부모 데이터가 삭제되었는데 자식 데이터가 그대로 남아있는 고아 데이터(Orphan Data)나 참조 불일치가 발생할 수 있다.

애플리케이션 계층의 3가지 보완 전략#

  1. 트랜잭션 내 연관 데이터 검증 철저히 수행
    • 자식 데이터를 생성·수정하기 전, 동일한 트랜잭션 범위 안에서 부모 데이터가 실제로 존재하는지 애플리케이션 로직(repository.existsById(...) 등)으로 먼저 검증한다.
  2. 부모 데이터 삭제 시 논리적 삭제(Soft Delete) 적용
    • 부모 레코드를 DELETE 쿼리로 물리 삭제하면 기존 자식 데이터들의 참조 대상이 사라지게 된다. 대신 deleted_at이나 is_deleted 플래그를 갱신하는 Soft Delete를 적용해 과거 주문·이력 데이터의 참조 무결성을 안전하게 보존한다.
  3. 배치 프로세스 및 정합성 검증 스케줄러 운영
    • 분산 환경이나 예외 상황으로 인해 간헐적으로 발생할 수 있는 고아 데이터를 막기 위해, 주기적으로 도는 배치(Batch) 작업이나 정합성 검증 스케줄러를 두어 연결이 끊어진 데이터를 탐지하고 정리한다.
