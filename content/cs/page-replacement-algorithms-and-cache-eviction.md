## 1. 페이지 교체 알고리즘이란?

가상 메모리를 사용하는 운영체제에서 물리 메모리(RAM)에 빈 공간(프레임)이 없을 때, **어떤 페이지를 디스크로 내보내고 새 페이지를 메모리에 올릴지 결정하는 규칙**을 <strong>페이지 교체 알고리즘(Page Replacement Algorithm)</strong>이라고 한다.

교육과정이나 각종 CS 시험에서도 단골로 등장하는 주제이지만, 단순히 시험용 이론에 그치지 않고 현대 서버 시스템의 성능을 좌우하는 핵심 기반 원리다.

---

## 2. 왜 페이지 교체 알고리즘이 항상 중요하게 다뤄질까?

### 1) 메모리와 디스크 간의 극심한 속도 차이

컴퓨터 시스템에서 가장 큰 병목 구간 중 하나는 **물리 메모리(RAM)와 보조기억장치(SSD/HDD)의 속도 격차**다. 두 계층의 접근 속도는 수천에서 수만 배 이상 차이가 난다.

페이지 교체가 한 번 잘못 일어나 곧바로 다시 쓸 페이지를 디스크로 쫓아내면, 곧장 페이지 부재(Page Fault)가 발생해 불필요한 디스크 읽기와 쓰기를 다시 수행해야 하고, 그 긴 시간 동안 CPU는 아무 일도 하지 못한 채 대기하게 된다.

### 2) 스레싱(Thrashing) 방지

교체 효율이 떨어지면 프로세스가 실제 연산 작업을 처리하는 시간보다 **페이지를 디스크와 RAM 사이에서 넣고 빼는 작업(Swapping)에만 매달리는 스레싱(Thrashing) 현상**이 발생한다. 스레싱에 빠지면 CPU 사용률이 급락하고 시스템 전체가 멈춘 것처럼 느려지기 때문에, 이를 막기 위한 효율적인 교체 전략이 필수적이다.

### 3) OS 커널을 넘어 모든 '캐시' 시스템으로 이어지는 원리

페이지 교체 원리는 운영체제 커널 내부에만 머물지 않는다. CPU 캐시, 데이터베이스 버퍼 풀, 웹 브라우저 캐시, CDN, Redis 같은 인메모리 캐시 시스템의 데이터 삭제(Eviction) 정책에도 똑같은 개념이 그대로 적용된다.

## 3. 대표적인 페이지 교체 알고리즘 5가지

| 알고리즘 | 교체 기준 | 핵심 특징 및 한계 |
| :--- | :--- | :--- |
| **FIFO** (First-In, First-Out) | 메모리에 **가장 먼저 들어온** 페이지 | 구현이 가장 단순하지만, 자주 쓰이는 페이지도 오래됐다는 이유로 쫓아낸다. 프레임을 늘려도 페이지 부재가 오히려 증가하는 <strong>벨라디의 모순(Belady's Anomaly)</strong>이 발생할 수 있다. |
| **OPT** (Optimal) | **앞으로 가장 오랫동안 쓰이지 않을** 페이지 | 이론상 페이지 부재가 가장 적은 최적의 알고리즘이지만, 미래의 참조 순서를 미리 알아야 하므로 실제 구현은 불가능하다. 다른 알고리즘을 평가하는 **이론적 기준선**으로 쓴다. |
| **LRU** (Least Recently Used) | **가장 오랫동안 사용되지 않은** 페이지 | *"최근에 쓴 데이터는 곧 다시 쓰인다"*는 <strong>시간 지역성(Temporal Locality)</strong>을 반영해 시험과 실무 캐시 시스템에서 가장 자주 다뤄진다. ([LRU 참고 정리](https://gymdev.tistory.com/60)) |
| **LFU** (Least Frequently Used) | **참조 횟수가 가장 적은** 페이지 | 많이 쓰인 데이터를 오래 남길 수 있지만, 과거에 누적 횟수가 많았던 데이터가 최근에는 안 쓰이는데도 메모리를 계속 차지하는 등 **최근 사용 흐름을 덜 반영**할 수 있다. |
| **NUR / 2차 기회 (Clock)** | **참조 비트(Reference Bit)** 등을 활용 | 각 페이지에 참조 비트와 변경 비트(Dirty Bit)를 두어 최근 사용 여부를 표시하고, 교체 후보가 되었을 때 비트가 1이면 0으로 바꾸며 **한 번 더 기회를 주는** 방식으로 LRU를 가볍게 근사한다. |

## 4. 백엔드 캐시 시스템에서 만나는 페이지 교체 원리

페이지 교체 알고리즘을 운영체제(OS)에서만 쓰는 개념으로 보기 쉽지만, 사실 서버 위에서 돌아가는 **모든 캐시 시스템의 근본 원리**다.

시스템 아키텍처는 언제나 <strong>"빠르고 비싸고 좁은 공간(메모리/캐시)"</strong>과 <strong>"느리고 싸고 넓은 공간(디스크/DB)"</strong>의 조합으로 이루어진다. 좁은 공간이 꽉 차면 결국 누군가를 버려야 하는데, 이때 쓰이는 규칙이 바로 위 알고리즘들이다.

- **Redis (인메모리 DB) 캐시 Eviction 정책**: 설정된 `maxmemory` 한계에 도달하면 `allkeys-lru`, `volatile-lru`, `allkeys-lfu` 등의 정책을 통해 어떤 키를 메모리에서 제거할지 결정한다.
- **Spring Boot 로컬 캐시 (Caffeine 등)**: 애플리케이션 서버의 한정된 JVM 힙(Heap) 메모리 안에서 캐시 개수가 한도에 달했을 때, LRU나 빈도 기반(TinyLFU 등) 정책으로 오래되거나 덜 쓰이는 엔트리를 비워낸다.
- **MySQL InnoDB Buffer Pool**: 디스크에 있는 데이터와 인덱스 페이지를 메모리에 캐싱해 두고, 변형된 LRU 알고리즘(Young/Old 서브리스트)을 통해 자주 조회되는 핫 페이지는 메모리에 오래 남기고 한 번만 읽고 지나가는 페이지는 빠르게 밀어낸다.

## 5. 결론

결국 페이지 교체 알고리즘이 풀고자 하는 문제는 하나로 요약된다.

> **"한정된 빠른 공간(메모리·캐시)이 꽉 찼을 때, 어떤 데이터를 버려야 시스템이 가장 덜 느려질까?"**

운영체제의 가상 메모리 관리부터 Redis 캐시 정책, MySQL 버퍼 풀 튜닝까지 모두 이 동일한 질문 위에서 동작하고 있다.
