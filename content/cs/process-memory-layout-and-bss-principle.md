## 1. 왜 프로세스 메모리를 4개의 영역으로 나눌까?

운영체제(OS)는 디스크에 있던 프로그램이 실행되어 프로세스(Process)가 되면, 실행에 필요한 독립적인 가상 메모리 공간을 할당한다. 이 공간은 데이터의 성격, 생명주기, 접근 권한에 따라 **Code, Data, Heap, Stack**의 4가지 영역으로 나뉜다.

현대 컴퓨터는 프로그램의 명령어와 데이터를 모두 같은 메인 메모리에 올려놓고 실행한다. 이때 메모리를 통째로 섞어 쓰지 않고, 다음 세 가지 질문을 거치면서 자연스럽게 4개 영역으로 분화된다.

1. **명령어인가, 데이터인가? (➔ Code 분리)**
   - 실행 중인 프로그램 코드가 버그나 해킹으로 인해 실수로 덮어씌워지면 시스템이 즉시 붕괴한다. 그래서 OS는 변하면 안 되는 명령어만 따로 모아 **읽기·실행 전용(Read/Execute)** 권한을 걸어 보호한다.
2. **수명이 영구적인가, 임시적인가? (➔ Data 분리)**
   - 명령어를 떼어내고 남은 것은 모두 읽고 쓸 수 있는 데이터다. 이 중 프로그램이 켜질 때부터 꺼질 때까지 계속 살아 있고 크기도 변하지 않는 데이터(전역·정적 변수)를 **Data** 영역으로 묶는다. 컴파일 시점에 주소와 크기가 확정되므로 실행 중 할당·해제 관리 비용이 들지 않는다.
3. **실행 중 생기는 데이터의 수명이 규칙적인가? (➔ Stack과 Heap 분화)**
   - 함수 호출 순서에 맞춰 규칙적으로 생겼다가 사라지는 데이터는 **Stack**으로, 수명과 크기를 예측할 수 없는 동적 데이터는 **Heap**으로 나뉜다.

```text
낮은 주소 (0x0000...)
┌──────────────────────────────┐
│          Code 영역           │  기계어 명령어 (Read / Execute 전용)
├──────────────────────────────┤
│      Data 영역 (초기화)      │  초기값이 있는 전역·정적 변수
├──────────────────────────────┤
│      BSS 영역 (미초기화)     │  초기값 없는(0) 전역·정적 변수
├──────────────────────────────┤
│          Heap 영역           │  동적 할당 (낮은 주소 ➔ 높은 주소)
│              ↓               │
│          (빈 공간)           │
│              ↑               │
│          Stack 영역          │  지역 변수, 매개변수 (높은 주소 ➔ 낮은 주소)
└──────────────────────────────┘
높은 주소 (0xFFFF...)
```

결국 이렇게 영역을 분리하는 이유는 **① 안전성(실행 코드 읽기 전용 보호)**, **② 생명주기별 관리 효율화**, **③ 컴파일 시점에 크기를 알 수 없는 동적 데이터와 함수 호출 깊이의 유동적 공간 활용**이라는 세 가지 목적 때문이다.

## 2. 4대 영역 상세 구조와 BSS의 절약 원리

### 1) Code 영역
- 작성한 소스 코드가 컴파일되어 변환된 **기계어 명령어**들이 저장된다.
- CPU는 이 영역에서 명령어를 하나씩 가져와(Fetch) 실행한다.
- 실행 중 코드가 임의로 변경되면 치명적인 오류가 발생하므로 **읽기 전용(Read-Only)** 권한으로 보호되며, 프로그램 시작 시 로드되어 종료 시까지 유지된다.

### 2) Data 영역 (Data vs BSS)
- <strong>전역 변수(Global)</strong>와 <strong>정적 변수(Static)</strong>가 저장된다. 함수 실행 후 버려지는 변수가 아니라 프로그램 시작부터 종료까지 살아 있고 크기도 고정되어 있기 때문이다.
- 실제 메모리와 실행 파일에서는 초기화 여부에 따라 두 구역으로 나뉜다.
  - **Data (Initialized Data)**: 초기값이 지정된 전역·정적 변수 (예: `int a = 10;`)
  - **BSS (Block Started by Symbol)**: 초기값이 없거나 `0`으로 초기화된 전역·정적 변수 (예: `int b;`). 실행 시 OS가 자동으로 `0`으로 초기화한다.

#### BSS 영역이 메모리를 절약하는 원리
핵심은 <strong>BSS 영역이 일차적으로 절약하는 대상이 실행 중인 RAM이 아니라 '디스크 공간(실행 파일의 크기)'</strong>이라는 점이다. 원리는 단순하다. *"어차피 전부 `0`으로 채울 데이터라면, 실행 파일 안에 `0`을 일일이 저장하지 않고 크기(숫자)만 적어두는 것"*이다.

예를 들어 크기가 약 **4MB**인 전역 배열을 선언했다고 가정해 보자.

- **Data 영역 (`int arr[1000000] = {1, 2, 3, ...};`)**:
  초기값이 제각각이므로 컴파일러는 실행 파일(Windows `.exe`, Linux `ELF`) 안에 이 **4MB 분량의 데이터를 통째로 기록**해야 한다. 결과적으로 실행 파일 크기가 그대로 4MB 늘어난다.
- **BSS 영역 (`int arr[1000000];` 또는 `= {0};`)**:
  어차피 실행 시점에 전부 `0`이 될 데이터다. 디스크에 `0`을 400만 바이트나 적어 넣는 것은 낭비이므로, 컴파일러는 실제 데이터를 넣지 않고 실행 파일 헤더에 <strong>"BSS 영역: 시작 주소 X, 크기 4MB"</strong>라는 메타데이터 **단 몇 바이트만 기록**한다. 이후 프로그램이 실행될 때 OS가 해당 크기만큼 RAM에 공간을 잡고 `0`으로 채워준다.

### 3) Heap 영역
- 개발자가 런타임(Runtime) 도중 필요에 따라 **동적으로 할당하는 데이터**가 저장된다. (C의 `malloc`, C++/Java의 `new`로 생성한 객체 등)
- **낮은 주소에서 높은 주소 방향**으로 자라며 크기가 유동적이다.
- C/C++에서는 개발자가 직접 해제(`free`, `delete`)해야 하고, Java·JavaScript·Python 같은 언어에서는 가비지 컬렉터(GC)가 사용하지 않는 객체를 자동으로 회수한다.

### 4) Stack 영역
- 함수 호출과 관련된 **지역 변수(Local)**, **매개변수(Parameter)**, **복귀 주소(Return Address)** 등이 **스택 프레임(Stack Frame)** 단위로 저장된다.
- **후입선출(LIFO, Last-In First-Out)** 구조로 동작하며, **높은 주소에서 낮은 주소 방향**으로 자란다.
- 함수가 호출되면 스택 프레임이 쌓이고(Push), 함수가 반환(종료)되면 즉시 제거(Pop)된다.

## 3. Heap과 Stack의 설계 특징

### 왜 Heap과 Stack은 서로 마주 보고 자랄까?

프로세스에 할당된 가상 메모리 공간은 한정되어 있다. 어떤 프로그램은 동적 할당(Heap)을 많이 쓰고, 어떤 프로그램은 깊은 함수 호출(Stack)을 많이 쓴다.

두 영역을 정해진 고정 크기로 미리 쪼개두는 대신 **가상 메모리 양 끝에 배치해 서로 마주 보며 자라게 하면**, 중간의 빈 공간을 상황에 따라 유연하게 나누어 쓸 수 있어 메모리 낭비를 최소화할 수 있다. 단, 두 영역이 서로의 경계를 침범하면 오버플로우가 발생한다.

### 왜 Stack은 Heap보다 훨씬 빠를까?

- **Stack**: 단순히 스택 포인터(SP)의 주소값을 더하거나 빼는 CPU 명령어 한 번으로 할당과 해제가 끝난다. 또한 메모리가 연속적으로 배치되어 있어 CPU 캐시 적중률(Cache Hit Rate)이 매우 높다.
- **Heap**: 할당할 때마다 크기에 맞는 빈 메모리 블록을 탐색해야 하고, 해제 시에도 포인터 추적이나 가비지 컬렉션(GC) 오버헤드가 발생하므로 상대적으로 느리다.

## 4. 대표적인 메모리 오류와 이 구조를 알아야 하는 이유

### 대표적인 메모리 오류 2가지

1. **Stack Overflow**: 종료 조건이 없는 재귀 함수를 호출하거나 너무 큰 지역 변수를 선언해 Stack 영역에 할당된 한계를 초과할 때 발생한다.
2. **Memory Leak (메모리 누수)**: Heap에 동적으로 메모리를 할당한 뒤 더 이상 사용하지 않는데도 해제하지 않아(또는 참조를 계속 물고 있어 GC가 회수하지 못해) 가용 메모리가 점차 고갈되는 현상이다.

### 결국 이 개념이 중요한 이유

C 같은 저수준 언어부터 Java, Python 같은 고수준 언어까지 결국 밑바닥은 이 **메모리 4대 영역** 위에서 돌아간다.

- 자바에서 <strong>원시 타입(Primitive)</strong>과 <strong>참조 타입(Reference)</strong>이 왜 다르게 동작하는지,
- <strong>가비지 컬렉터(GC)</strong>가 왜 Stack이 아니라 Heap 영역만 청소하는지,
- 서버에서 `StackOverflowError`나 `OutOfMemoryError`가 터졌을 때 어디를 살펴봐야 하는지

모두 이 4대 영역 구조에서 설명된다. 장애 대응과 성능 최적화의 출발점이 결국 여기서 시작되기 때문에, 백엔드 개발자라도 한 번쯤 바닥 구조를 정확히 짚고 넘어갈 필요가 있다.
