# 리프레시 토큰의 이원화: 하이브리드 환경에서의 세션 정합성 해결기

## 1. 서론: 왜 Access Token과 Refresh Token을 함께 쓰는가?

인증 시스템을 설계할 때 가장 먼저 마주하는 선택지는 '로그인 상태를 어떻게 안전하게 유지할 것인가'입니다. 현대적인 웹 서비스에서는 보안과 편의성의 균형을 위해 Access Token과 Refresh Token이라는 이중 토큰 체계를 주로 사용합니다.

*   **Access Token (액세스 토큰):** 실질적인 인증 수단입니다. 유효 기간이 매우 짧아(예: 30분~1시간) 탈취되더라도 피해를 최소화할 수 있습니다. 하지만 만료될 때마다 사용자가 다시 로그인해야 한다면 UX는 최악이 될 것입니다.

*   **Refresh Token (리프레시 토큰):** 액세스 토큰이 만료되었을 때, 새로운 액세스 토큰을 발급받기 위한 '보증서' 역할을 합니다. 보통 긴 유효 기간(예: 2주)을 가지며, 서버의 DB에 저장되어 안전하게 관리됩니다.

**작동 원리:** 사용자가 로그인하면 서버는 두 토큰을 모두 발급합니다. 클라이언트는 매 요청마다 액세스 토큰을 보냅니다. 그러다 액세스 토큰이 만료되어 401 Unauthorized 에러가 발생하면, 클라이언트는 저장해둔 리프레시 토큰을 서버에 보내 새로운 액세스 토큰을 갱신(Refresh)받습니다. 이 과정을 통해 사용자는 재로그인 없이도 매끄럽게 서비스를 이용할 수 있습니다.

💡 **개요: MYKOT 프로젝트에서 마주한 세션 만료의 늪**

이러한 표준적인 인증 아키텍처를 MYKOT 프로젝트에 적용하던 중, 결정적인 UX 결함을 발견했습니다. 바로 '단일 리프레시 토큰 정책'으로 인한 세션 충돌 문제입니다.

기존 시스템은 사용자당 단 하나의 refreshToken만을 발급하도록 설계되어 있었습니다. 하지만 하이브리드(네이티브 웹뷰 + 브라우저) 환경을 고려하지 못한 이 단순한 정책은, 사용자가 웹에서 활동하다가 앱으로 접속하는 순간 기존 웹 세션을 즉시 만료시켜버리는 결과를 초래했습니다. 플랫폼 간의 독립적인 활동을 보장하지 못했고, 결과적으로 사용자는 "왜 자꾸 로그아웃이 되는가?"라는 당혹감을 느끼게 되었습니다.

## 2. 본질적인 원인: 플랫폼 특성을 간과한 설계

분석 결과, 기존 방식은 하이브리드 환경의 특성을 충분히 반영하지 못한 "순진한(Naive)" 구조였습니다.

*   **단일 컬럼의 한계:** users 테이블의 단일 refresh_token 필드는 멀티 플랫폼 접속을 구분하지 못했습니다. 새로운 기기에서 로그인하면 기존 토큰을 덮어씌워 버렸습니다.

*   **추출 경로의 단일화:** 오직 쿠키(Cookie)에만 의존하는 방식은 보안 정책이 엄격하거나 쿠키 사용이 제한적인 앱(Native WebView) 환경에서 세션 관리를 불안정하게 만들었습니다.

*   **Fixed Timeout:** 사용자의 활동 여부와 관계없이 최초 발급 시점만을 기준으로 만료를 체크하여, 활발히 작업 중인 사용자가 예고 없이 강제 퇴장당하는 문제가 있었습니다.

## 3. 시행착오: 모든 세션을 개별 관리하려던 시도

처음에는 refresh_token을 별도로 관리하는 전용 테이블을 생성하여, 모든 브라우저(User-Agent)와 기기별 세션을 무한히 개별 저장하는 방식을 검토했습니다.

하지만 이 방식을 도입하려고 보니 다음과 같은 현실적인 문제에 부딪혔습니다.

*   **높은 결합도:** 기존에 구현된 공통 예외 처리(401 에러 핸들링 등) 및 보안 로직이 단일 토큰 구조에 깊게 결합되어 있어, 테이블 분리 시 코드 수정 범위가 감당하기 어려울 정도로 넓어지는 리스크가 있었습니다.

*   **구현 복잡도:** 모든 브라우저의 개별 세션을 일일이 관리하는 것은 유연하지만, 관리 포인트가 급격히 늘어나 시스템 오버헤드가 발생할 우려가 컸습니다.

## 4. 해결을 위한 아키텍처 재설계
'독립성 확보'와 '코드 유지보수성' 을 판별하여 Web/App 이원화 전략으로 구현하였습니다.

**엔티티(Entity) 레벨의 이원화**

사용자의 플랫폼 정보를 명확히 구분하기 위해 User 엔티티를 리팩토링하여 웹과 앱 전용 필드를 각각 구성했습니다.

```java
// User.java 중 일부
@Column(name = "web_refresh_token", columnDefinition = "TEXT")
private String webRefreshToken;

@Column(name = "app_refresh_token", columnDefinition = "TEXT")
private String appRefreshToken;

// 플랫폼별 토큰 접근 로직 추상화
public String getRefreshTokenByPlatform(String platform) {
    return "app".equals(platform) ? appRefreshToken : webRefreshToken;
}
```

**유연한 토큰 추출 (Hybrid Extraction)**

쿠키와 Refresh-Token 헤더를 동시에 탐색하도록 개선했습니다. 이를 통해 쿠키 사용이 제한적인 앱 환경에서도 헤더를 통해 토큰을 전달받아 DB의 토큰을 정상적으로 NULL 처리(로그아웃)할 수 있게 되었습니다.

**Sliding Session과 Absolute Timeout**

활동 중인 세션은 자동으로 연장(Sliding)하되, 보안을 위해 최초 로그인 후 일정 시간이 지나면 반드시 재인증을 받도록 '절대 만료 시간'을 도입했습니다.

## 5. 검증 결과: 실무 시나리오 테스트

설계 변경 후, 실제 발생할 수 있는 다양한 케이스를 바탕으로 안정성을 확인했습니다.

| 테스트 케이스       | 수행 동작                                  | 기대 결과 및 확인 내용                                                              |
| ----------------- | ----------------------------------------- | ----------------------------------------------------------------------------------- |
| 웹 중복 로그인     | 브라우저 A 로그인 후 B 로그인                     | A에서 요청 시 중복 로그아웃 처리 (DB에는 B의 토큰 유지)                                         |
| 유휴 세션 정리     | 로그인 후 아무 활동 없음                             | 30초~1분 뒤 Heartbeat 감지로 자동 로그아웃 처리                                               |
| 플랫폼 독립성     | 웹과 앱 동시 로그인                               | 각각 독립적인 토큰 생성 및 기능 사용 시 상호 간섭 없음 확인                                         |
| 로그아웃 독립성   | 웹/앱 로그인 중 웹만 로그아웃                        | web_refresh_token만 null, app_refresh_token은 유지됨                                      |
| 멀티 탭 환경       | 동일 브라우저 내 탭 A, B 이용                         | 탭을 이동하며 활동해도 세션이 유지되며 로그아웃되지 않음                                             |

## 6. 마치며

이번 리팩토링은 단순히 기능을 수정한 것이 아니라, 복잡한 테이블 설계와 효율적인 필드 분리 사이에서 최적의 해답을 찾아가는 과정이었습니다.

이를 통해 사용자 인증 관리에 대해 한층 더 깊이 알게 되었고, 무조건적인 확장성보다는 현재 시스템의 아키텍처와 결합도를 고려한 선택이 실제 서비스 운영에 더 큰 안정성을 준다는 것을 깨달았습니다.
