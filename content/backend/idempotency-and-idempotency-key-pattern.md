## 1. 멱등성(Idempotency)이란?

쉽게 말해 멱등성은 <strong>"결제 버튼을 두 번 눌렀다고 내 돈이 두 번 빠져나가지 않게 막는 성질"</strong>이라고 볼 수 있다. 조금 더 정확히 정의하면, <strong>동일한 연산을 한 번 실행하든 여러 번 연속으로 실행하든 시스템의 상태와 결과가 정확히 동일하게 유지되는 성질</strong>을 뜻한다.

### 일상적인 비유로 이해하기

- **멱등한 경우 (엘리베이터 버튼)**: 5층 버튼을 1번 누르면 5층에 불이 켜지고 엘리베이터가 5층으로 이동한다. 급하다고 5층 버튼을 10번 연타하더라도 결과는 여전히 "5층으로 이동"으로 똑같다.
- **멱등하지 않은 경우 (자판기 동전 투입)**: 1,000원 버튼을 1번 누르면 1,000원이 들어가지만, 10번 누르면 10,000원이 들어간다. 누를 때마다 상태가 누적되어 변하므로 멱등하지 않다.

## 2. HTTP 메서드로 보는 멱등성

HTTP 스펙에서도 각 메서드가 기본적으로 멱등성을 가지는지 구분하고 있다.

| 구분 | HTTP 메서드 | 동작 특성 및 예시 |
| :--- | :--- | :--- |
| **멱등함** | `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE` | `DELETE /users/10`을 1번 호출하든 10번 연달아 호출하든 <strong>"10번 유저는 삭제된 상태"</strong>로 서버 리소스 상태가 같다. `PUT` 역시 같은 데이터로 리소스를 전체 대체하므로 결과가 달라지지 않는다. |
| **멱등하지 않음** | `POST`, `PATCH` | `POST /orders` (5만 원 결제)를 10번 호출하면 매번 새로운 주문과 결제가 생성되어 통장에서 50만 원이 빠져나간다. |

따라서 서버 상태를 변경하거나 새 리소스를 생성하는 `POST`, `PATCH` 같은 메서드에 멱등성을 제공하려면 **애플리케이션 서버와 DB 차원에서 직접 멱등성을 구현**해야 한다.

## 3. 분산 시스템에서 멱등성이 필수인 이유

현대의 백엔드 시스템은 서버 한 대로만 돌아가지 않는다. 모바일 앱, 여러 대의 마이크로서비스(MSA), 외부 PG사 등이 네트워크를 통해 통신한다. 분산 환경에서는 네트워크 지연, 타임아웃, 서버 장애로 인해 **클라이언트가 보낸 요청이 중복 전송(Retry)되거나 순서가 뒤섞이는 일**이 언제든 벌어질 수 있다.

```text
[스마트폰 앱] ──────(1. 5만 원 결제 요청)──────> [쇼핑몰 서버]
                                                     │ (2. 카드 결제 정상 승인 완료)
[스마트폰 앱] <──(3. 성공 응답 패킷 유실 / Timeout)── [쇼핑몰 서버]
```

1. 사용자가 지하철에서 결제 버튼을 누른다.
2. 서버는 결제를 정상적으로 5만 원 처리 완료한다.
3. 그런데 순간적으로 지하철 와이파이가 끊겨 **"결제 성공" 응답 패킷이 스마트폰으로 돌아가지 못한다 (Timeout Error).**
4. 앱이나 사용자는 에러가 났다고 판단해 *"실패했나 보네? 다시 결제해야지"* 하고 재시도(Retry) 요청을 보낸다.

이때 서버에 멱등성 처리가 되어 있지 않다면, **이미 결제가 완료된 건임에도 사용자 통장에서 5만 원이 또 빠져나가는 이중 결제 사고**로 이어진다.

## 4. 해결책: 멱등키(Idempotency Key)와 테이블 패턴

이 문제를 막는 핵심 아이디어는 **요청(주문)마다 유일한 '번호표(UID)'를 붙여서 보내는 것**이다.

클라이언트(앱/웹)가 결제 요청을 보낼 때 HTTP 헤더에 고유한 난수 키를 실어 보낸다.

```http
POST /api/payments
Idempotency-Key: pay-uuid-987654321
```

서버는 이 `pay-uuid-987654321`이라는 번호표를 보고 *"이미 내가 5만 원 결제 처리를 끝낸 번호표네?"* 라고 판단해 **결제 로직은 건너뛰고, 기존에 저장해 둔 성공 응답 결과만 그대로 돌려준다.**

### 멱등키 테이블 패턴의 DB 동작 흐름

토스, 스트라이프(Stripe) 같은 결제·핀테크 시스템에서는 멱등성을 보장하기 위해 RDBMS에 **멱등키 전용 테이블**을 두고 `PRIMARY KEY`(또는 `UNIQUE`) 제약조건을 활용한다.

```sql
CREATE TABLE idempotency_records (
    idempotency_key VARCHAR(100) PRIMARY KEY,
    status          VARCHAR(20),
    response_body   TEXT,
    created_at      DATETIME
);
```

요청이 들어왔을 때 DB 내부에서는 다음과 같이 분기 처리된다.

```text
[클라이언트 요청 도착 (Idempotency-Key 포함)]
   │
   ▼
┌────────────────────────────────────────────────────────┐
│  DB의 idempotency_records 테이블에 INSERT 시도          │
└────────────────────────────────────────────────────────┘
   │                                       │
(1. 처음 온 번호표 - INSERT 성공)       (2. 중복된 번호표 - PK 충돌 에러 발생)
   │                                       │
   ▼                                       ▼
[비즈니스 로직(결제) 정상 실행]          [테이블에 저장된 기존 response_body 조회]
   │                                       │
   ▼                                       ▼
[결과 JSON을 테이블에 UPDATE]            [비즈니스 로직 실행 없이 기존 응답만 반환]
   │
   ▼
[정상 응답 반환]
```

1. **첫 번째 요청**:
   - `INSERT INTO idempotency_records (idempotency_key, status) VALUES ('pay-123', 'PROCESSING')` 가 성공한다.
   - 실제 결제 로직을 실행하고 완료되면 `status = 'COMPLETED'`, `response_body = '{"orderId": 1}'`로 업데이트한 뒤 응답을 반환한다.
2. **두 번째 중복 요청 (네트워크 재시도)**:
   - 똑같이 `INSERT`를 시도하지만, DB의 **PK(Unique) 제약조건**에 의해 `DuplicateKeyException` 같은 중복 키 에러가 발생한다.
   - 서버는 이를 예외 장애가 아니라 <strong>"이미 처리 중이거나 처리가 끝난 요청"</strong>으로 인식하고, 테이블을 조회해 저장된 `response_body`를 꺼내어 결제 로직은 전혀 실행하지 않고 응답만 그대로 반환한다.

## 5. 분산 시스템과 카프카(Kafka) 환경에서의 핵심 포인트

### Q1. 결제 시스템이나 카프카(Kafka) 컨슈머에서 중복 요청·메시지가 들어올 때 데이터 정합성을 어떻게 지킬까?

네트워크 타임아웃이나 브로커 재전송으로 인한 중복 처리를 방지하기 위해 **멱등키(Idempotency Key) 테이블 패턴**을 적용할 수 있다. 요청이나 메시지마다 고유한 멱등키를 발급해 RDBMS의 Unique 제약조건으로 선점(INSERT) 처리를 해두면, 동일한 키로 중복 요청이 들어오더라도 **실제 비즈니스 로직은 최초 1회만 실행되고 이후 요청에는 기존에 저장해 둔 결과를 안전하게 반환**하여 데이터 정합성을 지킬 수 있다.

### Q2. 분산 시스템에서 '정확히 한 번(Exactly-Once)' 처리가 어려운 이유와 해결책은?

네트워크 통신에는 성공과 실패 외에 <strong>'알 수 없음(응답 패킷 유실)'이라는 제3의 상태</strong>가 존재하기 때문에, 타임아웃 시 재전송(Retry)이 불가피하다.

따라서 분산 시스템에서는 인프라 레벨에서 완벽한 1회 전송을 기대하기보다, **인프라는 '최소 한 번(At-Least-Once)' 전송을 보장하고, 요청을 수신하는 애플리케이션이 '멱등성(Idempotency)'을 갖추어 결과적으로 Exactly-Once와 동일한 효과**를 내도록 설계하는 것이 정석이다.
