## 1. 들어가며: 왜 인덱스의 내부 구조를 알아야 할까?

백엔드 개발을 하다 보면 조회 성능을 높이기 위해 자연스럽게 인덱스를 걸게 된다. 하지만 단순히 자주 조회하는 컬럼에 인덱스를 추가한다는 수준에 머무르면, 인덱스를 걸어두고도 100만 건의 데이터를 모두 뒤지는 **Full Table Scan**을 마주하거나 잘못된 복합 인덱스 순서로 인해 디스크와 메모리만 낭비하기 쉽다.

인덱스가 언제 동작하고 언제 무력화되는지 정확히 판단하려면, RDBMS가 채택한 **B+Tree**의 물리적 구조와 정렬 특성을 먼저 이해해야 한다.

## 2. 왜 Hash Table이나 B-Tree가 아닌 B+Tree인가?

### 1) Hash Table vs B+Tree: 탐색 속도 `O(1)`을 포기한 이유

탐색 시간 복잡도만 놓고 보면 해시 테이블(Hash Table)은 `O(1)`로 B+Tree의 `O(log N)`보다 빠르다. 그럼에도 RDBMS 인덱스가 해시 테이블 대신 B+Tree를 기본으로 사용하는 이유는 **해시 함수의 특성**에 있다.

- **해시 함수의 목적**: 충돌(Collision)을 방지하기 위해 입력 데이터를 최대한 겹치지 않고 골고루 분산시키는 것이다.
- **치명적인 한계**: 데이터를 균등하게 퍼뜨리는 과정에서 <strong>원래 데이터가 가진 대소 관계와 연속성(정렬 순서)</strong>이 완전히 파괴된다.

결과적으로 해시 인덱스는 단건 동등 비교(`=`)에는 강력하지만, 실무 쿼리의 대부분을 차지하는 <strong>범위 검색(`>`, `<`, `BETWEEN`)</strong>, <strong>정렬(`ORDER BY`)</strong>, <strong>전방 일치 검색(`LIKE 'abc%'`)</strong>에서는 인덱스를 전혀 활용할 수 없어 테이블 전체를 뒤져야 한다.

### 2) B-Tree vs B+Tree: 목차와 본문의 분리

B+Tree는 대용량 데이터를 디스크(보조기억장치)에 저장하고 빠르게 탐색하기 위해 기존 **B-Tree의 단점을 보완하여 발전된 형태**다. 책의 목차에 비유하면 두 구조의 차이가 명확해진다.

- **B-Tree**: 목차 페이지 중간중간에 실제 책 본문(데이터)이 섞여 있는 형태다. 루트나 브랜치 노드를 탐색하다가 운 좋게 찾는 데이터가 있으면 그 자리에서 읽고 탐색을 끝낸다.
- **B+Tree**: 상위 노드(Non-Leaf Node)는 **순수하게 목차(이정표) 역할**만 수행한다. 실제 본문 데이터(클러스터드 인덱스의 레코드 또는 세컨더리 인덱스의 PK 값)는 오직 맨 아래 <strong>리프 노드(Leaf Node)</strong>에만 모여 있으며, 리프 노드들끼리는 <strong>양방향 연결 리스트(Doubly Linked List)</strong>로 이어져 있다.

예를 들어 `회원ID(PK)`와 `회원 정보`가 저장된 테이블을 비교해 보자.

```text
[B-Tree 노드 내부]
노드 하나에 [10번: 홍길동, 주소...], [20번: 이영희, 주소...] 처럼 Key와 실제 데이터가 함께 저장됨
→ 데이터 크기가 크다 보니 한 페이지(InnoDB 기준 16KB) 안에 몇 건 담지 못함

[B+Tree 노드 내부]
┌─ Non-Leaf 노드 (순수 이정표) ────────────────────────────────────────┐
│ "10보다 작으면 왼쪽, 10~20 사이면 가운데, 20보다 크면 오른쪽으로 이동" │
│ → 오직 Key(숫자)와 자식 노드 주소 포인터만 저장 (실제 데이터 없음)    │
└──────────────────────────────────────────────────────────────────────┘
                                 ↓
┌─ Leaf 노드 (맨 아래, 양방향 연결 리스트로 연결) ─────────────────────┐
│ [10번: 홍길동, 주소...] ⇄ [11번: 김철수, 주소...] ⇄ [20번: 이영희...] │
│ → 여기에만 실제 회원 정보가 사전순으로 정렬되어 모여 있음            │
└──────────────────────────────────────────────────────────────────────┘
```

### 3) 메모리 캐싱(Buffer Pool)과 디스크 I/O 측면의 이점

이처럼 브랜치 노드(Non-Leaf)에서 무거운 데이터를 빼고 가벼운 Key와 포인터만 남기면 두 가지 결정적인 이점이 생긴다.

1. **트리의 높이(Depth) 최소화 (높은 Fan-out)**: 한 페이지(16KB) 안에 수백~수천 개의 Key를 빽빽하게 담을 수 있으므로, 데이터가 수천만 건으로 늘어나도 트리의 높이는 대개 **3~4단계**에 불과하다.
2. **InnoDB Buffer Pool 캐싱 효율 극대화**: 브랜치 노드의 크기가 매우 작아 메모리(Buffer Pool)에 상주시켜 두기 유리하다. 자주 접근하는 상위 레벨 노드는 메모리에서 즉시 읽고, 실제 디스크 I/O는 마지막 리프 노드를 읽는 1회 수준으로 줄어든다.

### 4) 모든 탐색 경로의 길이가 같다는 것(`O(log N)`)의 의미

- **B-Tree**는 찾는 데이터가 루트 노드에 있으면 1번(`O(1)`), 리프 노드에 있으면 여러 번(`O(log N)`) 접근해야 하므로 쿼리마다 <strong>응답 속도의 편차(Jitter)</strong>가 발생한다.
- **B+Tree**는 모든 실제 데이터가 리프 노드에만 존재하므로 어떤 데이터를 찾더라도 항상 `루트 노드 ➔ 브랜치 노드 ➔ 리프 노드`로 이어지는 **동일한 횟수의 탐색 경로**를 거친다. 즉, 어떤 요청이 들어와도 항상 예측 가능하고 일정한 응답 속도를 보장한다는 운영상의 신뢰성을 제공한다.

## 3. B+Tree의 동작 메커니즘과 복합 인덱스(Composite Index)

B+Tree 인덱스는 리프 노드에 데이터를 <strong>사전순(정렬된 상태)</strong>으로 저장하고, 리프 노드 간 양방향 연결 리스트를 통해 범위 스캔을 수행한다. 이 구조적 특징에서 **복합 인덱스**의 핵심 규칙들이 파생된다.

### 핵심 동작 메커니즘 4가지

1. **트리 분기 탐색**: 루트 노드에서 브랜치 노드로 내려가며 Key 값을 비교해 탐색 범위를 좁혀 나간다 (`O(log N)`).
2. **리프 노드 도달 및 연속 스캔**: 정렬된 리프 노드에서 조건이 시작되는 지점을 찾은 뒤, 범위 검색(`BETWEEN`, `>=`, `<`)의 경우 트리를 다시 오르내리지 않고 리프 노드의 연결 리스트를 따라 옆으로 쭉 읽어나가는 **Index Range Scan**을 수행한다.
3. **좌측 접두사 원칙 (Leftmost Prefix)**: 복합 인덱스 `(A, B)`는 **A 컬럼으로 먼저 정렬하고, A 값이 같을 때만 B 컬럼으로 정렬**하는 구조다. 따라서 `WHERE` 절에 선행 컬럼 `A` 없이 후행 컬럼 `B`만 단독으로 사용하면 정렬 순서를 활용할 수 없어 인덱스를 타지 못한다.
4. **컬럼 가공의 함정**: `WHERE` 절에서 인덱스 컬럼을 함수나 연산으로 감싸면, 인덱스 트리에 저장된 **원본 Key 값**과 형태가 달라져 트리 탐색이 불가능해진다.

## 4. 실전 쿼리 비교: 인덱스를 죽이는 쿼리 vs 살리는 쿼리

100만 건의 데이터가 들어있는 `users` 테이블에 복합 인덱스 `idx_created_phone (created_at, phone)`이 생성되어 있다고 가정해 보자.

### Bad Pattern: 인덱스가 무효화되어 Full Table Scan으로 추락하는 경우

```sql
-- 1. 인덱스 컬럼을 함수로 가공 (원본 Key 비교 불가 → Full Table Scan)
SELECT * FROM users WHERE DATE(created_at) = '2026-11-02';

-- 2. 앞자리 와일드카드(%) 사용 (사전순 정렬 기준 상실 → Full Table Scan)
SELECT * FROM users WHERE phone LIKE '%5678';

-- 3. 복합 인덱스(created_at, phone)에서 선행 컬럼(created_at) 누락
SELECT * FROM users WHERE phone = '010-1234-5678';
```

### Good Pattern: 정렬 구조를 온전히 활용하여 Index Range Scan을 유도하는 경우

```sql
-- 1. 컬럼은 원본 그대로 두고, 비교할 상수 값을 범위 조건으로 변환
SELECT * FROM users 
WHERE created_at >= '2026-11-02 00:00:00' 
  AND created_at < '2026-11-03 00:00:00';

-- 2. 앞자리 고정 접두사 검색 (사전순 시작점을 찾아 Index Range Scan 작동)
SELECT * FROM users WHERE phone LIKE '010-1234%';

-- 3. 선행 컬럼(created_at)을 반드시 포함하여 복합 인덱스 활용
SELECT * FROM users 
WHERE created_at >= '2026-11-01 00:00:00' 
  AND phone = '010-1234-5678';
```

> **참고 (3번 쿼리의 동작 범위):** 3번 쿼리처럼 선행 컬럼(`created_at`)에 범위 조건(`>=`)이 들어가면, `created_at`까지는 인덱스 탐색 범위를 결정하는 데 쓰이지만 그 뒤의 `phone = '010-1234-5678'` 조건은 리프 노드 스캔 범위를 줄이는 조건이 아니라 읽은 인덱스 레코드를 걸러내는 **필터링(Filtering) 조건**으로만 동작한다. 이 점이 바로 복합 인덱스의 컬럼 순서를 정할 때 가장 중요하게 작용한다.

## 5. 복합 인덱스 `(A, B, C)` 컬럼 순서를 결정하는 기준

그렇다면 여러 컬럼을 묶어 복합 인덱스를 설계할 때 어떤 컬럼을 앞에 두어야 할까? 핵심 기준은 다음 순서로 요약할 수 있다.

> **[1순위: 동등(`=`) 조건] ➔ [2순위: 정렬(`ORDER BY`)] ➔ [3순위: 범위(`>`, `<`, `BETWEEN`) 조건]**
>
> 동일한 조건 내에서는 <strong>카디널리티(Cardinality, 고유값의 수)</strong>가 높은 컬럼을 앞으로 배치한다.

### 1) 동등(`=`) 조건 컬럼을 범위(`>`, `<`, `BETWEEN`) 조건보다 앞에 둔다
복합 인덱스 `(A, B, C)`에서 선행 컬럼 `A`가 범위 조건으로 조회되는 순간, `A`의 범위 안에서는 `B`와 `C`의 전체 정렬 순서가 깨진다. 따라서 **범위 조건이 등장한 이후의 컬럼들은 인덱스 탐색 범위를 좁히는 데 사용되지 못하고 단순 필터링 용도로만 작동**한다.

반면 `WHERE A = ? AND B = ? AND C > ?`처럼 동등 조건 컬럼들을 앞쪽에 배치하면, `A`와 `B`가 고정된 상태에서 `C` 역시 완벽하게 정렬된 상태를 유지하므로 세 컬럼 모두 인덱스 범위 스캔에 온전히 기여할 수 있다.

### 2) 동일한 동등(`=`) 조건끼리는 카디널리티(선택도)가 높은 컬럼을 앞에 둔다
예를 들어 `성별(남/여)`처럼 중복도가 높은 컬럼보다, `이메일`이나 `휴대폰 번호`처럼 고유한 값의 종류가 많은(**카디널리티가 높은**) 컬럼을 앞에 배치하면 첫 번째 조건만으로도 검색 대상을 훨씬 빠르게 압축할 수 있어 탐색 효율이 높아진다.

## 6. 핵심 요약

1. **B+Tree의 구조적 강점**: 브랜치 노드에 데이터를 두지 않고 오직 Key와 포인터만 담아 트리 높이를 낮추고 Buffer Pool 캐싱 효율을 극대화하며, 리프 노드의 양방향 연결 리스트로 빠른 범위 탐색(Range Scan)과 일정한 탐색 시간(`O(log N)`)을 보장한다.
2. **인덱스 무효화 방지**: 인덱스 컬럼을 함수나 연산으로 가공하지 않고, `LIKE` 검색 시 좌측 접두사가 고정되도록 쿼리를 작성해야 정렬 특성을 유지할 수 있다.
3. **복합 인덱스 설계 공식**: **좌측 접두사 원칙**에 따라 반드시 조회 조건에 포함되는 컬럼을 선행에 배치하되, **동등(`=`) 조건 컬럼을 앞쪽에, 범위 조건 컬럼을 뒤쪽에** 배치하고 카디널리티가 높은 컬럼을 우선순위로 둔다.
